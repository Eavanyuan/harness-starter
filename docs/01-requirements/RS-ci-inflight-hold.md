# RS-ci-inflight-hold：在途流水不关账 + 跨流水轮次上限 + 本地轮次互斥（change，关联 ci-fail-trigger）

> S 档 rs。行为细节见 `FS-任务循环执行器.md` §4.4（同批更新）。

## 1 背景与痛点

定时修复执行器上线后第一个小时的实况（2026-11-17 17:12–18:15）暴露三个机制缺口：

1. **在途流水被误关账**：执行器 18:10 向 !1847 推修复 → 新流水 running → "非 failed 即不在触发集" → 18:14 sweep 把它当"已合并/已批红/已关闭"关账（删 ack/工单、释放认领）。若该流水随后转红，虽会重新认领，但中间账目是假的（关账理由凭空捏造），且存在无账窗口。
2. **没有跨流水轮次上限**：!1896 round-1 修复推送后失败项 13→16（越修越坏的实况）。每条新流水=新认领=预算重置，"修→推→红→再修"可无限循环，每 30 分钟推一个可能更坏的 commit。maxRounds=3 只约束单认领，从未真正生效。
3. **本地轮次可并发**：launchd 心跳 180s 而一轮可跑 10s+；轮次一旦超心跳就有第二份进程并发。认领有 CAS 仲裁，但 sweep/ack 写盘没有互斥。

另：执行器没有 GitLab 凭据（设计如此：会话永不持凭据），opaque 工单只能给 8 行摘录，1847 的 e2e 失败行执行器根本看不到。

## 2 用户故事

- **作为**：定时修复的使用者
- **我希望**：推送后的流水在跑时账目保持、自动修复有总轮次上限、并发轮次互斥、opaque 时执行器拿得到全量日志
- **以便**：环路账实一致，坏循环会被截停而不是无限重试

**验收标准**

- Given 我的 MR 流水**非终态**（running/pending/created/manual/canceled/skipped/未知字串，或推送后流水尚未创建的秒级窗口）When sweep Then 不关账、不重认领（"流水在跑——账目保持"）；只有终态 **success**（或 MR 合并/关闭）才关账，**failed** 走重认领重归因——终态白名单只认 success/failed，其余一律保守保持
- Given 同一 MR 第 N 条失败流水（跨流水累计）When 第 N 次归因且 N>maxRounds Then `state:needs_human` + `ci_escalated` + 无新工单（旧工单删除）——升级给人，人工处置后自动恢复
- Given 上一轮仍在进行（锁 <30min）When 新 tick Then 本轮跳过；孤儿锁（>30min）接管照跑；正常退出自清锁
- Given opaque 归因 Then 失败 job 的 trace 尾部 400 行落 `.ai/task-loop/traces/<id>/`，工单指路——执行器读文件不读凭据
- ack.ci 新增 `rounds`（跨流水累计）与 `projectId` 字段

## 4 非功能约束

- 终态白名单只认 success/failed：其余（含 canceled/skipped——人停的流水，等新推送或人工处理，claim TTL 24h 兜底升级）与未知状态字串、无流水（推送→创建的秒级窗口）一律保守按在途保持——方向是"多保持一会儿"而非"误关账"
- 轮次锁是保险不是门禁：锁判不了（非 EEXIST 异常）时放行，不过度保守
- trace 尾部每 job 400 行、opaque 时才落盘（体积可控）

## 5 范围外

- 飞书侧在途语义（无 CI 概念）；跨 MR 的全局并发度治理

## 6 术语表

- **在途（inflight）**：流水非终态（在跑/排队/待手动触发）——触发不可能成立，但"消失"也未证实
- **rounds（跨流水累计）**：同一 MR 第几次因新失败流水被归因；1=首轮，>maxRounds 升级
- **needs_human**：自动修复的截停终态——保留引入清单供人看，不再出工单

## 7 开放问题

- 轮次锁与跨机：锁是本机的（多机由 CAS 认领仲裁，本机并发是 launchd 单机问题）
- needs_human 的自动恢复路径目前只有"人工推新流水/关 MR"；是否加定时提醒（订阅卡片）留 T2 演进
