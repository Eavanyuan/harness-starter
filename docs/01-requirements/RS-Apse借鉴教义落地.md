# RS-Apse 借鉴教义落地

> 任务：`.ai/tasks/apse-doctrine/state.json`（S 档，feature）。
> 来源：外部系统复盘《Apse：从 Agent 循环到漏洞处理与挖掘》（TDengine，2026-11-07），用户在会话中定案「第 1、2 条落地，其余记 retro 候选」。

## 1 背景与痛点

Apse 的预算死锁事故（停机判断放在被停对象里面→整机停摆）与 maker-checker 局限（同类模型评审抓共有盲区失败、CI 才暴露）是两条经过生产验证的通用教训，正是本仓库 checklist 与 CR 模板的题材。其余六项借鉴需等触发条件，预防性建设反而制造维护面。

## 2 用户故事

### US-1 教义沉淀进既有消费点

- **作为**：后续写门禁/调度逻辑的人
- **我希望**：停机位置错误这个失效形态出现在我动手前必读的清单里
- **以便**：不用再踩一次 Apse 已用生产事故演示过的坑

**验收标准**

- Given checklist.md When 查第 37 条 Then 含「停机判断在上一层/停机动作不抛异常/先落盘再传播/墙钟与成本分开/阻塞要有回来的路」五条判据，并标注外部样本来源
- Given CR 模板头 When 读引用块 Then 验证阶梯按伪造成本排序且写明「模型评审是过滤器不是证据；🔴 处置权在人」

### US-2 其余候选可追溯不丢失

- **作为**：未来立项的人
- **我希望**：六项未落地借鉴各自写明触发条件与落点
- **以便**：条件出现时直接按落点开工，不重新考古

**验收标准**

- Given retro 候选文件 When 查任一条目 Then 触发条件与落点两列均非空，且含「已对齐不重建」的判断依据
- Given 六项候选中任一条 When 触发条件未出现 Then 仓库中不存在该条目的实现代码（防预防性建设）

## 4 非功能约束

不动代码与判定逻辑；check-skills/gate 全绿；不提前实现候选项（防预防性建设）。

## 5 范围外

候选 1-8 的实现本身；预算三维（需 state schema 变更，走正式立项）。

## 6 术语表

- **停机在边界**：预算/重试/超时的判定放在被停对象的上一层，由调度层执行，不由被停执行体自报。
- **验证阶梯**：证据按伪造成本排序——脚本判据 < 同类模型评审 < CI/verify 日志 < 人。
- **认知投降**：人保留了批准权，却没有足够时间与证据做判断（批次越大越易发生）。
