## 1 背景与痛点

task-loop 已经能自动处理三类活：飞书 bug 单、MR 的 CI 失败、评审打回。它是**无人值守**的——
判得了就自己走，判不了就升级。这带来两个问题，都在过去两周实际发生过：

1. **上下文读得太少就下判断。** 11-23 的 P1 单 7176122491：loop 只读了 5 个字段，判「信息不全
   （缺复现步骤/日志）」，去追问提交者。实测那张单有 996 字的复现步骤、一份 17 页的 PDF（证据文件 `search_by_mql.fields`）。
   追问本身是误判。
2. **很多活本来就不该无人值守。** 需求类工作项、涉及行为变更的修复、信息分散在文档里的任务，
   需要人先确认「我理解的是不是你要的」，再动手。现在没有这个入口，人只能把内容手工贴进对话。

用户要的是一条**有人把关的**路：给定一个飞书工作项，把能读的都读了，给出任务类型建议，
人确认之后再交给 coding agent；中途遇到需要人定的事，停下来问。

## 3 用户故事

### US-1 一条命令读全工作项

- **作为**：开发者
- **我希望**：`harness feishu <工作项ID或链接>` 把工作项里能读到的内容都读出来
- **以便**：不用手工把飞书内容复制进对话，也不会因为少读了字段而误判

**验收标准**

- Given 工作项 ID 或链接 When 执行命令 Then 输出名称、类型、状态、负责人、描述及配置的补充字段
- Given 工作项有附件 When 执行命令 Then 附件被下载到任务目录，记录文件名、大小、类型与解析出的文本
- Given 描述里有链接 When 执行命令 Then 链接被列出并标注读取状态（`已读` / `未读取：无读取能力` / `未读取：需授权`）
- Given 某项读取失败 When 执行命令 Then 失败项和原因出现在摘要里，命令**不把该项当作不存在**
- Given 字段 key 随空间不同 When 执行命令 Then 按字段中文名从该空间的字段配置解析 key；解析不到则报出字段名
- Given 工作项类型没有配置的某个字段 When 执行命令 Then 该字段标为「该类型没有此字段」并写进未读取清单，不中断
- Given 描述里有内嵌图片或评论带附件 When 执行命令 Then 与附件字段一样下载并记录状态

### US-2 先给人看，再动手

- **作为**：开发者
- **我希望**：命令给出任务类型建议、影响范围和待决问题，我确认之前不创建任何任务档案、不启动 agent
- **以便**：分类错了能当场改，而不是修完才发现做的是另一件事

**验收标准**

- Given 读取完成 When 生成摘要 Then 包含：来源链接、已读取/未读取清单、需求摘要、建议类型（`feature` / `change` / `bugfix`）、建议档位、影响范围
- Given 建议类型 When 展示 Then 附带**依据**（来自哪些字段/附件的哪句话），没有依据的建议标为「无依据」
- Given 用户未确认 When 命令结束 Then 没有创建 `state.json`、没有修改飞书工作项
- Given 分类不确定或材料互相矛盾 When 生成摘要 Then 逐条列为待决项，每项带可选项和推荐
- Given 规则给不出类型建议 When 展示 Then 明确标为「无建议」，并列出可选类型让人选
- Given 生成摘要时该文件被人改过（首行没有生成标记） When 生成 Then 不覆盖并提示，人的编辑不被冲掉；补充材料写 `NOTES.md`，工具只读不写
- Given 人补充了材料（`NOTES.md`）When 重新生成摘要 Then 摘要里列出补充的内容与字数

### US-3 确认之后才落地

- **作为**：开发者
- **我希望**：确认后创建任务档案，未答的待决问题挡住后面的流程；回答之后才启动 coding agent
- **以便**：范围由我把关

**验收标准**

- Given 用户用 `--confirm <类型> --by <名字>` 明确确认 When 确认 Then 创建任务档案，`--type` 用确认后的类型，来源工作项写进档案
- Given 确认的类型不在 `feature|change|bugfix` 里、缺 `--by`、读取结果不存在，或工作项在读取之后有更新 When 确认 Then 拒绝建档并说明原因，不留下任何文件
- Given 类型是 `change` When 确认 Then 必须带需求基线提交，否则拒绝
- Given 确认时还有未答的待决问题 When 建档 Then 问题写成 `human_decision` blocker 写进档案，流程停在当前阶段；回答走 `resume`
- Given agent 执行中出现超范围的行为变更或架构决策 When 执行 Then 写入 `human_decision` blocker 并停下，给出恢复命令
- Given 建档完成 When 用仓库校验核对 Then 新档案通过（工具写下的状态必须能过自己的门禁）

### US-4 本版不对飞书做任何写操作

- **作为**：开发者
- **我希望**：读取、确认、建档全过程不改飞书工作项（不流转状态、不发评论、不改字段）
- **以便**：自动流程不会在我不知情时对外发消息

**验收标准**

- Given 任何阶段 When 读取或确认 Then 对飞书只发出白名单内的读取请求；出现白名单外的工具名时直接报错，请求不发出
- Given 确认建档完成 When 复核调用记录与任务档案 Then 调用记录里只有白名单内的读取工具，确认人与确认时间已记入档案（不记名的确认不存在）


## 4 核心需求

一条命令、两个阶段。**读取与摘要阶段不产生任何副作用**（不建任务档案、不改飞书）；确认后才进入执行阶段。

```text
harness feishu <工作项ID或链接>                 # 只读：读取并生成摘要
  │
  ├─ 阶段一：读取 + 摘要（只读）
  │    1. 解析工作项：ID / 链接 → project_key + work_item_id + 工作项类型
  │    2. 解析字段 key：按配置的字段中文名，从该空间字段配置查 key（每次运行都查，不缓存跨空间）
  │    3. 取内容：MQL 取描述类字段、附件字段；评论；关联工作项
  │    4. 取附件：逐个下载到任务目录，能解析的解析出文本，不能解析的保留原文件并标注
  │    5. 提取描述与富文本里的链接，逐个标注读取状态
  │    6. 生成摘要：来源 / 已读 / 未读 / 需求摘要 / 建议类型与档位 / 影响范围 / 待决项
  │    7. 把摘要落到 .ai/intake/<工作项ID>/summary.md，命令结束
  │
  └─ 阶段二：确认 + 执行（有副作用，每一步都要人点头）
       8. 人看摘要：类型建议、依据、待决问题；要补材料就写 NOTES.md 再重跑（回到第 6 步）
       9. 人明确确认类型 → 创建任务档案，来源工作项写进档案
      10. 未答的待决问题写成 human_decision 阻断，流程停在当前阶段；用 resume 逐条回答后
          才启动 coding agent；执行中遇到需要人定的事同样写成阻断并停下
      11. 交付报告：改动、验证证据、未完成项
      12. （本版不做）回写飞书：留待后续，届时需单独授权
```

| R2 | 字段按中文名配置、运行时按工作项类型的字段表解析 key；类型映射走配置表 | `harness.rules.json` 的 `runtime.feishu.intake` 配置节 | US-1 |

## 5 非功能约束

- **读取只读**：除 US-4 明确授权的操作外，对飞书只有读请求。
- **来源可追**：每条进入任务上下文的内容都带来源（字段名 / 附件名 / 评论 ID）与读取时刻。
- **摘要可重放**：读取结果落在任务目录；重跑同一条命令得到同一份摘要，不重复下载。
- **解析器可选**：解析失败时保留原文件并标注「未解析」，不阻断流程。
- **可恢复**：确认中断后重跑同一条命令，得到同一份摘要，不重复读取已读内容。
- **不入 git**：下载的附件与解析出的文本落在 `.ai/intake/<工作项ID>/`，该目录整目录忽略，不进版本库。
- **不依赖 PDF 解析器的特定实现**：解析失败时保留原文件并标注「未解析」，不阻断流程。

## 6 范围外

- 读取飞书云文档、多维表格正文（MCP 无此能力，见 §2.2-A）。
- 图片/截图附件的内容识别。
- 回写飞书（状态流转、评论）。本版不实现，读取层只允许白名单内的读取工具。
- **检查需求内容本身是否自洽。** 规则只看得到类型名、描述长短、行为变更字段，读不懂内容。
  实测：一张单的描述写「SEC-001–003」，附件里有 SEC-001–010 共 10 个——规则照样判「bugfix、把握高、0 项待决」。
  这类矛盾只能靠人读摘要与附件时发现。要机器发现，得交给模型并要求给出依据（开放问题 3 的下一步）。
- 修改 task-loop 的自动认领逻辑。本功能是独立入口。

## 7 术语表

- **工作项**：飞书项目里的任务/缺陷/需求实例。
- **MQL**：飞书项目的查询语言，`search_by_mql` 工具用它按字段取数。
- **读取状态**：每条来源内容的三态之一——已读、未读取（附原因）、读取失败（附原因）。
- **待决项**：需要人做选择的点，落成 `human_decision` blocker。
- **档位**：S / M / L / XL，决定流程要经过哪些阶段。

### 实现时对照现有代码做的两处调整

- **待决问题的回答放在建档之后。** 原设想是「答完所有问题再建档」。仓库里已有现成的一套：把问题写成 `human_decision` blocker，用 `resume` 逐条回答并记名。所以流程改为：确认类型 → 建档，未答的问题作为阻断写进档案 → 用 `resume` 回答 → 流程才继续。这样不用另造一套回答机制，也满足「人确认之前不动手」。
- **本版不做任何飞书写操作。** 原设想是「回写需单独授权」，本版直接不实现：读取层只允许白名单内的读取工具，白名单外的工具名直接报错。回写留待以后单独做。
