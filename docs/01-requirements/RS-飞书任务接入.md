## 1 背景与痛点

task-loop 已经能自动处理三类活：飞书 bug 单、MR 的 CI 失败、评审打回。它是**无人值守**的——
判得了就自己走，判不了就升级。这带来两个问题，都在过去两周实际发生过：

1. **上下文读得太少就下判断。** 11-23 的 P1 单 7176122491：loop 只读了 5 个字段，判「信息不全
   （缺复现步骤/日志）」，去追问提交者。实测那张单有 996 字的复现步骤、一份 17 页的 PDF（证据文件 `search_by_mql.fields`）。
   追问本身是误判。
2. **很多活本来就不该无人值守。** 需求类工作项、涉及行为变更的修复、信息分散在文档里的任务，
   需要人先确认「我理解的是不是你要的」，再动手。现在没有这个入口，人只能把内容手工贴进对话。

用户要的是一条**有人把关的**路：给定一个飞书工作项，把能读的都读了，给出任务类型建议，
人确认之后再交给 coding agent；中途遇到需要人定的事，停下来问。

## 3 用户故事

### US-1 一条命令读全工作项

- **作为**：开发者
- **我希望**：`harness task feishu <工作项ID或链接>` 把工作项里能读到的内容都读出来
- **以便**：不用手工把飞书内容复制进对话，也不会因为少读了字段而误判

**验收标准**

- Given 工作项 ID 或链接 When 执行命令 Then 输出名称、类型、状态、负责人、描述及配置的补充字段
- Given 工作项有附件 When 执行命令 Then 附件被下载到任务目录，记录文件名、大小、类型与解析出的文本
- Given 描述里有链接 When 执行命令 Then 链接被列出并标注读取状态（`已读` / `未读取：无读取能力` / `未读取：需授权`）
- Given 某项读取失败 When 执行命令 Then 失败项和原因出现在摘要里，命令**不把该项当作不存在**
- Given 字段 key 随空间不同 When 执行命令 Then 按字段中文名从该空间的字段配置解析 key；解析不到则报出字段名

### US-2 先给人看，再动手

- **作为**：开发者
- **我希望**：命令给出任务类型建议、影响范围和待决问题，我确认之前不创建任何任务档案、不启动 agent
- **以便**：分类错了能当场改，而不是修完才发现做的是另一件事

**验收标准**

- Given 读取完成 When 生成摘要 Then 包含：来源链接、已读取/未读取清单、需求摘要、建议类型（`feature` / `change` / `bugfix`）、建议档位、影响范围
- Given 建议类型 When 展示 Then 附带**依据**（来自哪些字段/附件的哪句话），没有依据的建议标为「无依据」
- Given 用户未确认 When 命令结束 Then 没有创建 `state.json`、没有修改飞书工作项
- Given 分类不确定或材料互相矛盾 When 生成摘要 Then 逐条列为待决项，每项带可选项和推荐

### US-3 确认之后才落地

- **作为**：开发者
- **我希望**：确认后创建任务档案并启动 coding agent，agent 遇到需要我定的事就停下来
- **以便**：范围由我把关

**验收标准**

- Given 用户明确确认类型与范围 When 确认 Then 创建任务档案（`--type` 用确认后的类型），来源工作项 ID 写入档案
- Given 确认时需要补充信息 When 用户补充 Then 重新生成摘要再确认，不跳过确认
- Given agent 执行中出现超范围的行为变更、架构决策、或关键材料读不到 When 执行 Then 写入 `human_decision` blocker 并停下，给出恢复命令
- Given 执行结束 When 交付 Then 汇总改动、验证证据、未完成项

### US-4 回写飞书必须单独确认

- **作为**：开发者
- **我希望**：是否更新飞书工作项（状态流转、评论）由我单独决定
- **以便**：自动流程不会在我不知情时对外发消息

**验收标准**

- Given 任何阶段 When 未获得回写授权 Then 不对飞书做任何写操作
- Given 用户授权回写 When 交付后 Then 仅执行授权的操作，并在报告里逐条列出做了什么

## 4 核心需求

一条命令、两个阶段。**读取与摘要阶段不产生任何副作用**（不建任务档案、不改飞书）；确认后才进入执行阶段。

```text
harness task feishu <工作项ID或链接> [--repo <业务仓>]
  │
  ├─ 阶段一：读取 + 摘要（只读）
  │    1. 解析工作项：ID / 链接 → project_key + work_item_id + 工作项类型
  │    2. 解析字段 key：按配置的字段中文名，从该空间字段配置查 key（每次运行都查，不缓存跨空间）
  │    3. 取内容：MQL 取描述类字段、附件字段；评论；关联工作项
  │    4. 取附件：逐个下载到任务目录，能解析的解析出文本，不能解析的保留原文件并标注
  │    5. 提取描述与富文本里的链接，逐个标注读取状态
  │    6. 生成摘要：来源 / 已读 / 未读 / 需求摘要 / 建议类型与档位 / 影响范围 / 待决项
  │    7. 把摘要落到 .ai/intake/<工作项ID>/summary.md，命令结束
  │
  └─ 阶段二：确认 + 执行（有副作用，每一步都要人点头）
       8. 人看摘要：改类型、改档位、答待决项、补材料（补了就回到第 6 步重新出摘要）
       9. 人明确确认 → 创建任务档案，来源工作项 ID 写入 meta
      10. 启动 coding agent；需要人定的事写成 human_decision blocker 并停下
      11. 交付报告：改动、验证证据、未完成项
      12. 回写飞书：仅在人单独授权后执行，逐条报告
```

## 5 非功能约束

- **读取只读**：除 US-4 明确授权的操作外，对飞书只有读请求。
- **来源可追**：每条进入任务上下文的内容都带来源（字段名 / 附件名 / 评论 ID）与读取时刻。
- **摘要可重放**：读取结果落在任务目录；重跑同一条命令得到同一份摘要，不重复下载。
- **解析器可选**：解析失败时保留原文件并标注「未解析」，不阻断流程。
- **可恢复**：确认中断后重跑同一条命令，得到同一份摘要，不重复读取已读内容。
- **敏感内容**：下载的附件与解析文本落在任务目录；该目录是否入 git 沿用现有 `.ai/` 约定（待决，见 §8 开放问题第 2 条）。
- **不依赖 PDF 解析器的特定实现**：解析失败时保留原文件并标注「未解析」，不阻断流程。

## 6 范围外

- 读取飞书云文档、多维表格正文（MCP 无此能力，见 §2.2-A）。
- 图片/截图附件的内容识别。
- 评论附件与描述内嵌图片的下载（`get_download_url` 的描述称支持，**未验证**）。
- 修改 task-loop 的自动认领逻辑。本功能是独立入口。

## 7 术语表

- **工作项**：飞书项目里的任务/缺陷/需求实例。
- **MQL**：飞书项目的查询语言，`search_by_mql` 工具用它按字段取数。
- **读取状态**：每条来源内容的三态之一——已读、未读取（附原因）、读取失败（附原因）。
- **待决项**：需要人做选择的点，落成 `human_decision` blocker。
- **档位**：S / M / L / XL，决定流程要经过哪些阶段。

## 8 开放问题（需要用户决定）

1. **入口形态**：`harness task feishu <id>`（GPT 建议）还是 `harness feishu <id>`？现有子命令都是单个词。
2. **附件与解析文本是否入 git**：PDF 可能有几百 KB；`.ai/` 目前整体入库。建议默认不入 git、只入库提取出的文本摘要。
3. **「未读取的链接文档」怎么处理**：只列出来让人自己看（保守），还是尝试用别的凭据读（需要额外接入飞书云文档 API，超出当前 MCP）。
4. **档位与类型的建议谁来定**：规则（关键词 + 字段）足够透明但粗糙；交给模型判断更准但需要说明依据。建议 MVP 用规则 + 要求模型给出依据。
5. **飞书里的工作项类型映射**：飞书的「需求/任务/缺陷」怎么对应到 `feature/change/bugfix`，是否需要配置表。
