# 快速上手：从零到 task-loop 跑起来

> 这是一份按顺序照做就能跑通的指南。每一步都有"怎么确认做对了"的检查点。

---

## 第一步：把 harness 装进你的项目

### 新项目

```bash
# 1. clone 本仓库
git clone https://github.com/Eavanyuan/harness-starter.git

# 2. 用 harness-cli 装进你的项目（或直接用当前仓库）
node harness-starter/scripts/harness-cli.mjs init /path/to/your-project

# 3. 进项目跑体检
cd /path/to/your-project
npm run doctor     # 模板态只提醒不报红
npm run gate       # 必须全绿（20 组自测）
```

### 存量项目

```bash
# 先看项目长什么样（只读，不动任何文件）
node harness-starter/scripts/harness-cli.mjs detect /path/to/project

# 看依赖图和风险（只读）
node harness-starter/scripts/harness-cli.mjs analyze /path/to/project --out /tmp/report

# 预览会装什么（不落盘）
node harness-starter/scripts/harness-cli.mjs init /path/to/project --dry-run

# 确认后装
node harness-starter/scripts/harness-cli.mjs init /path/to/project
```

**✅ 检查点**：`npm run gate` 全绿。红了就先修——那是 harness 自检，不是你的代码问题。

### 你会得到什么

```
你的项目/
├── .ai/tasks/          ← 任务状态（一个任务一份 state.json）
├── .ai/verify/         ← 验证证据日志（入库，CI 校验用）
├── agents/             ← 11 个 agent 定义（唯一事实源）
├── hooks/              ← 三道门 + 校验核心
├── scripts/            ← 全部工具（router/ai-review/task-loop/broker 等）
├── harness.rules.json  ← 审核路由规则（改这里不改代码）
├── AGENTS.md           ← 常驻规则（所有 CLI 都读）
├── .claude/  .zcode/   ← 生成物（不要手改）
└── ...
```

## 第二步：接 GitLab

### 2.1 创建 PAT（Personal Access Token）

1. GitLab → 你的头像 → **Preferences** → **Access Tokens**
2. 名字随便填（如 `task-loop`），勾选 scope：`api`
3. 点 Create，**立刻复制**（只显示一次）

```bash
export GITLAB_URL="https://gitlab.你的域名.com"
export GITLAB_TOKEN="glpat-xxxxxxxxxxxx"

# ✅ 检查点：30 秒确认凭据对不对
curl -s -H "PRIVATE-TOKEN: $GITLAB_TOKEN" "$GITLAB_URL/api/v4/user"
# 200 + 你的用户信息 = 通；401 = token 错
```

### 2.2 装 CI Runner（runner 是流水线的执行引擎）

在能访问 GitLab 的一台 Linux 机器上：

```bash
# Docker 方式（推荐）
docker run -d --name my-runner --restart always \
  -v /srv/gitlab-runner/config:/etc/gitlab-runner \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitlab/gitlab-runner:latest

# 注册到你的项目（token 从 GitLab 项目设置 → CI/CD → Runners 里拿）
docker exec -it my-runner gitlab-runner register \
  --url "$GITLAB_URL" \
  --token "glrt-xxxx" \
  --executor docker \
  --docker-image "node:22" \
  --description "my-runner"
```

**⚠️ 坑（实测踩过）**：镜像必须带 bash（alpine 没有，会 exit 127）。用 `node:22` 或在 CI 配置里 `before_script: apk add bash`。

**✅ 检查点**：`npm run doctor` 看到 `CI runner 在场` 绿条。

### 2.3 项目加 CI 配置

在项目根加 `.gitlab-ci.yml`（参考模板 `deploy/task-loop/gitlab-ci.example.yml`）：

```yaml
stages: [test]
variables:
  GIT_DEPTH: "0"    # 坑：不加的话 router 测试在 shallow clone 下假红

your-tests:
  stage: test
  image: node:22
  script:
    - bash test/your-suite.test.sh
```

### 2.4 配 broker 的 GitLab webhook（通知自动化用）

```bash
# 起 broker（需要飞书 webhook，见第三步；没配飞书也能跑，只是不发卡片）
GITLAB_URL=$GITLAB_URL \
GITLAB_TOKEN=$GITLAB_TOKEN \
GITLAB_WEBHOOK_SECRET=my-secret \
FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/xxx \
node scripts/harness-broker.mjs --port 8788
```

GitLab 项目 → **Settings** → **Webhooks** → 填 `http://<broker机器>:8788/webhook/gitlab`，secret 同上，勾 Merge request + Pipeline 事件。

**✅ 检查点**：`curl http://localhost:8788/healthz` 返回 `{"ok":true}`。

## 第三步：接飞书项目

### 3.1 拿 MCP 凭据

在[飞书项目](https://project.feishu.cn)里，让管理员：

1. 空间设置 → **开放能力** → MCP → 给你的应用勾选**工作项数据读取**（和写入，如果需要回写状态）
2. 拿到 `mcpKey` 和你的 `userKey`

### 3.2 配到 harness.rules.json

```json
{
  "runtime": {
    "feishu": {
      "projectKey": "你的空间key",
      "workItemType": "Defect",
      "severity": {
        "field": "field_xxxxx",
        "fieldName": "严重级别",
        "map": { "高": "P1", "中": "P2", "低": "P3" }
      }
    }
  }
}
```

**怎么找这些值**：`projectKey` 是空间 URL 里那段；`workItemType` 和 `field` 参考[飞书项目字段配置](https://project.feishu.cn/open/apis/docs)。

### 3.3 OAuth 登录（首次）

```bash
node scripts/feishu-auth.mjs login
# 浏览器打开 → 授权 → 凭据自动落 ~/.harness/task-loop/feishu-oauth.json（0600）
```

**✅ 检查点**：

```bash
node scripts/task-loop.mjs --once --profile b --dry-run
# 应列出指派给你的待处理缺陷单（P0/P1 自动 / P2 待确认）
```

**如果报 `Check Token Perm Failed`**：后台没勾"工作项数据读取"，找管理员加。

## 第四步：起 task-loop

### 4.1 装定时器（每 3 分钟自动跑一轮）

```bash
# 装到当前仓库（自动识别 macOS launchd / Linux systemd）
bash scripts/install-task-loop.sh .

# 查看状态
bash scripts/install-task-loop.sh . --status

# 停止（kill switch）
touch .ai/task-loop/OFF

# 恢复
rm .ai/task-loop/OFF

# 彻底卸载
bash scripts/install-task-loop.sh . --uninstall
```

**✅ 检查点**：`--status` 显示 `launchd: loaded` 或 `systemd timer: active`，`kill switch: off`。

### 4.2 影子周（安全试跑，零写入）

```bash
# 手动跑一次看会触发什么（不认领、不推代码、不发评论）
node scripts/task-loop.mjs --once --dry-run

# 跑一周积累数据后出报告
node scripts/task-loop.mjs --report
```

**验收**：报告显示 `唯一触发 ≥ 30` 且 `误触发 = 0` 才进下一步。

### 4.3 真跑

影子周过了，去掉 `--dry-run` 就是真跑。task-loop 会：

1. 轮询你的 MR（有没有被打回）和飞书缺陷单（有没有 P0/P1 指派给你）
2. 有的话：认领 → 起一个 AI 会话读评论/bug 详情 → 确认理解 → 修复 → 推分支 → CI → 等人审
3. 全程事件入账本（`.ai/ledger/events.jsonl`），可随时 `npm run ledger:report` 查看

## 第五步：日常使用

### 发起一个任务

```bash
# 新功能
bash scripts/init-harness.sh my-feature M

# 修 bug（关联原任务）
bash scripts/init-harness.sh my-fix M --type bugfix --related my-feature

# 飞书来的 bug
bash scripts/init-harness.sh feishu-hotfix M --type bugfix --related feishu:7161559257
```

### CLI 里用

```
/task 做一个按标签筛选列表的功能
```

### 审核自动化（MR 推上去自动跑）

```bash
# 在 CI 里加（.gitlab-ci.yml）
review:rs:
  rules: [{ if: '$CI_PIPELINE_SOURCE == "merge_request_event"', changes: ["docs/01-requirements/**"] }]
  script: node scripts/ai-review.mjs --type rs --base "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
```

## 常见问题

| 症状 | 原因 | 解法 |
|---|---|---|
| `bash: not found`（CI） | alpine 镜像没 bash | 换 `node:22` 或加 `before_script: apk add bash` |
| `Check Token Perm Failed`（飞书） | MCP 应用没勾数据读取 | 后台加权限 |
| `approved_by 为空` | 没人批红 | lead 在 MR 上点 approve |
| task-loop 每轮都触发同一 MR | discussion 没 resolve | 修复推送后手动 resolve 或等 task-loop 自动做 |
| `git push origin main` 被拒 | deva 没权限推保护分支 | 用 lead 凭据推，或走 MR |
