# 多人协作下的 Agent 落地

> 一句话回答标题里的问题：**不是二选一。知识留在 prompt，约束必须代码化，编排走半自动。**
>
> 本文给判据、给冲突点、给治理规则。不含"最佳实践"式的形容词。

---

## 一、先说结论

| 类型 | 载体 | 为什么 |
|---|---|---|
| **知识**（怎么做：编码规范、模块约定、业务背景） | prompt / skill（markdown） | 需要人读、需要频繁改、需要举例。代码化只会变成一堆没人维护的 DSL |
| **约束**（不许做什么：跳测试、改契约、删数据） | 代码（hook + CI） | 必须确定性。靠"大家都记得"的约束，在多人协作里等价于没有 |
| **编排**（谁在什么时候做什么） | 状态机 JSON + prompt 驱动 | 顺序固定，但"该不该停"需要语义判断。纯代码会僵化，纯 prompt 会漂移 |

判据一句话：

> **能被机器判定的，一律代码化；需要语义理解的，留在 prompt。**
> 两者都不成立的（比如"这次改动质量高不高"），就不要假装能自动化，交给人。

## 二、两个常见的错误方向

### 错误 A：全 prompt（很多人现在的做法）

现象：11 个 agent 定义写得很漂亮，门禁写在 prompt 里，比如"你必须跑完测试才能标记完成"。

多人协作下会坏在哪：

1. **约束力 = 模型自觉 × 模型能力。** 三个人用三个模型，其中一个人用的是弱模型，这条规则对他就不存在。
2. **无法审计。** 出事后你只能说"prompt 里写了"，但说不出"这次到底有没有执行"。
3. **漂移不可见。** 有人本地改了自己的 agent 文件没提交，行为和别人不一样，而且没人发现。

一句话：**prompt 里的"必须"，实际上是"建议"。**

### 错误 B：全代码化（另一种过度反应）

现象：把 agent 写成脚本，用 YAML 描述流程，用 DSL 定义决策。

会坏在哪：

1. **agent 的价值恰恰在语义判断。** 需求里的歧义、FS 与代码的冲突、审查里的"这处性能有问题"——这些写不进 if-else。
2. **维护成本压垮小团队。** 3 人团队养不起一套自研 DAG 引擎。
3. **僵化。** 真实任务的流程是变的，硬编码的流程会在第三周开始被绕过，然后被整体废弃。

一句话：**代码化的应该是"判定"，不是"判断"。**

## 三、多人协作的 7 个真实冲突点

这些问题单人时不存在或可以忍，三个人以上必然发生。

### 1. CLI 不统一 → 行为不一致

三个人用 Claude Code / ZCode / DeepSeek，工具名不同、hook 协议不同、subagent 支持不同。
手写三套的结局：三个月后没人说得清哪套是对的。

**解法**：单一源 `agents/*.agent.md` + 能力抽象 + 生成器 + CI 漂移检测。
本仓库的 `npm run check:agents` 就是这条：产物和源不一致，PR 直接挂。

> 漂移检测比生成本身更重要。只生成不检测，等于允许手改"生而不养"。

**同一个道理适用于 hook 接线**：`hooks/hooks.manifest.json` 是唯一源，`build:hooks` 生成
`.claude/settings.json` 与 `.zcode/config.json`，`check:hooks` 进 CI。
上一版只生成 agent、不生成接线，于是 ZCode 会话里三道门全不存在，而所有人的印象里"门禁是有的"。
接线差异不是格式细节，是事实差异：

| | Claude Code | ZCode | DeepSeek 独立调用 |
|---|---|---|---|
| hook 配置文件 | `.claude/settings.json` | `.zcode/config.json`（需 `hooks.enabled: true`） | 无 |
| 钩子形态 | `{type:'command', command:'node x.mjs'}` | `{type:'process', command:'node', args:['x.mjs']}` | — |
| matcher | `Bash\|Read` | `^(Bash\|Read)$`（JS 正则，必须锚定） | — |
| 生效前提 | 无 | 首次运行需人工信任工作区 hook | — |
| 兜底 | CI | CI | **只有 CI** |

### 2. 模型能力不同 → 强模型嫌烦、弱模型守不住

**解法**：分层豁免，但只豁免**脚手架**，不豁免**证据**。

| 可豁免 | 不可豁免 |
|---|---|
| 逐 TODO 提醒、分级提示、进度注入 | verify 证据链、审计四项、门禁判定 |

`harness.config.json` 的 `modelTiers` 定义分层；豁免清单要集中，不能散落在各 skill 里。

**必须配套一条退出条件**：连续两个季度没有任何豁免诉求，就删掉整个豁免机制。
只增不减的豁免清单，是设计腐化最诚实的信号。

### 3. 并行任务抢同一个状态文件

**解法**：一个任务一个 `.ai/tasks/<slug>/state.json`，一个任务一个 worktree。
合并时出现两份 state 是**正确行为**，按 `meta.created_at` 串行推进，不要手工合并成一份。

### 4. 门禁被绕过（人类手动 commit 是直通路）

本地 hook 只拦 agent 走的那条路。人 `git commit -m "hotfix"` 直接绕过。

**解法**：CI 是唯一裁决。本仓库 `hooks/lib/verify.mjs` 被 hook 和 `scripts/ci-verify.mjs` **共用同一份**——
这不是为了省代码，是为了保证两边判定一致。两边不一致时，人一定会走松的那条。

**但"共用"不等于"同强度"**：本地 hook 在工作树里跑，mtime 是真事实，可以判"日志是不是这次改完才跑的"；
CI 在全新 checkout 上跑，git 不保存 mtime，只认"文件在不在、日志进没入库、退出码是不是 0"。
上一版把 mtime 判据搬到 CI，结果合规 PR 被判红——门禁误杀好人的代价，是全套门禁被人关掉。
所以 `verify.mjs` 用 `mode: 'local' | 'ci'` 显式分开，不是偷偷放宽。

### 5. 豁免变成人情

`waived` 一旦可以口头给，三个月内会变成常态。

**解法**：三条硬规则。
- `waived` 必须带 `waived_by`，无记名按 `fail` 计（`ci-verify.mjs` 会拦）
- 月度统计 waived 率，**> 20% 说明门禁设计失败，不是团队纪律差**
- 处置方式是改门禁，不是放宽豁免

### 6. 新人第一天用不起来

老人能跑，是因为他知道"要先看 state""要跑 build"。
新人不知道，于是他绕开整套体系，直接和 AI 聊天——然后所有治理失效。

**解法**：
- 根目录 `AGENTS.md`，**70 行内**（`doctor` 会盯这个数），只回答"这是什么、现在在哪、找谁、不许做什么"
- 一条命令起步：`npm run doctor && npm run build:agents && npm run build:hooks && npm run gate`
- 三个入口写清楚：`/task`、`/rs`、`/impl`

### 7. agent 定义被随手改

有人觉得 prompt 啰嗦，删了两行"硬规则"，本地生效、提交后影响所有人。

**解法**：
- `agents/` 加 CODEOWNERS，改动需 harness owner review
- 改完必须 `npm run build:agents`，CI 校验漂移
- 改 prompt 等同于改生产代码，要有理由
- **机器侧**：`agents/`、`hooks/`、`templates/`、`harness.config.json` 属于受保护区，
  `guard_write` 会拒绝 agent 在任务中改它们；确需改由人加带到期日的放行条（`hooks/write-allowlist.txt`）

最后一条是这套治理表里唯一"不靠自觉"的部分。前面几条都是规范，只有它是机制。
判断要不要把某条规则升级成机制，问一句：**违反它的时候，有没有人会发现？** 没有，就得做成机制。

## 四、谁改什么（治理表）

| 文件 | 谁能改 | 评审要求 | 改错的后果 |
|---|---|---|---|
| `agents/*.agent.md` | 任何人 | 1 人 review + build + 门禁自测 | 全员 agent 行为改变 |
| `harness.config.json` | harness owner | 同左 | 安全边界变化 |
| `hooks/**.mjs` | harness owner | **必须新增测试用例** | 门禁失效且可能静默 |
| `hooks/hooks.manifest.json` | harness owner | 同左 + `check:hooks` | 某个 CLI 的门禁静默消失 |
| `.claude/settings.json`、`.zcode/config.json` | 生成物，任何人不得手改 | `check:hooks` | 同上（手改会在下次 build 被覆盖） |
| `hooks/write-allowlist.txt` | harness owner | 必须写原因 + 到期日 | 临时例外变成永久后门 |
| `test/*.test.sh` | harness owner | 同左 | 无法证明门禁可用 |
| `.skills/<stack>/SKILL.md` | 该栈 owner | 1 人 review + `check:skills` + 版本号 +1 | 编码 agent 按错规则工作，且没人发现 |
| `.skills/*/references/**` | 该栈 owner | 删规则需说明理由 | 规则悄然消失 |
| `scripts/check-skills.mjs` | harness owner | **必须新增测试用例** | 校验器变哑，skill 静默失效 |
| `.ai/rules/verification.md` | 任何人 | 2 人 review（L0 是宪法） | 底线被侵蚀 |
| `.ai/rules/L1-*.md` | 任何人 | 附事故链接（无事故不立规） | 规则变噪声 |
| `.ai/tasks/<slug>/**` | 任务发起人 | 不跨任务改 | 进度被覆盖 |
| `.ai/verify/*.log` | 只追加 | 禁止手工编辑 | 证据链失去意义 |

**一条硬规则**：`hooks/` 与所有校验脚本（`scripts/check-*.mjs`、`test/*.test.sh`）的改动，
如果没有对应的测试场景，一律不合并。
门禁代码和业务代码不一样——**它坏掉的时候不会报错，只会静默放行**。
这一类 bug 的形态在新项目里已经出现过两次：根路径多退一层导致全部命令被拦、
无提交仓库上 `--diff` 把"git 报错"当成"没有改动"。

## 五、按团队规模的落地节奏

数字是经验值，请用自己团队的数据校准。

| 规模 | 建议 | 理由 |
|---|---|---|
| 1–2 人 | 只上 `.ai/rules` + `guard_state` + 两个只读 agent | 人少时口头同步有效，流程税不值得 |
| 3–8 人 | 全量 11 agent + CI 门禁 + 月度体检 | 沟通成本开始超过流程成本，是这套体系的甜点区 |
| > 8 人 | 按模块拆 `.ai/rules/L2`，harness owner 轮值 | 单一 owner 会成为瓶颈 |

### 四周节奏

| 周 | 做什么 | 不做什么 |
|---|---|---|
| 第 1 周 | 只读 agent（RA/TS/SR）+ 3 张模板 + `guard_state` | 不装写码 agent |
| 第 2 周 | CI 门禁 + 第一条 L1 规则（**必须来自真实事故**） | 不写第 2–30 条规则 |
| 第 3 周 | coder 上线，信任级别 L1（只出草稿） | 不给自动合权限 |
| 第 4 周 | retro + 月度体检 10 问 | 不扩到第二个项目 |

## 六、反模式清单

| 反模式 | 症状 | 为什么坏 |
|---|---|---|
| 一开始就 11 个 agent 全开 | 第一周很爽，第三周没人用 | 门禁没跑通，出事后无法归因 |
| 一开始写 30 条规则 | 上下文被稀释 | 一条都记不住 |
| 一开始定 90% 覆盖率 | 存量项目第一周被卡死 | 阈值必须基于实测 |
| 让模型判断"这是不是高危操作" | 偶尔拦对，经常漏 | 高危必须黑名单硬拦 |
| 手改生成物 | 下次 build 就没了 | 漂移从此不可见 |
| 豁免清单只增不减 | 半年后豁免项比规则多 | 说明流程本身有问题，不是执行有问题 |
| 用 agent 讨论"要不要开始" | 每次都要人确认 | 停点设计错误，不是模型不听话 |

## 七、成本，诚实版

这套东西不是免费的：

| 成本项 | 量级 | 说明 |
|---|---|---|
| 前期搭建 | 1–2 人日 | 本仓库已铺好，主要是替换占位符与写第一个栈 skill |
| 日常流程税 | 每任务 15–30% 时间 | 写 RS/FS、跑门禁、填 state |
| 维护 | 每人每月 1–2 小时（估算） | 补规则、看 waived 率、修误拦 |
| token | 比裸聊高 1.5–2× | 加载 skill + 读写工件的开销 |

**回本的前提**：任务有重复性、需求变更不是每天翻盘、团队 ≥ 3 人。
不满足这三条，收益很可能为负。

---

## 八、什么时候不要用

- 团队 < 3 人，且项目周期 < 6 个月
- 没有 CI，或 CI 结果不可信
- 没有一个人愿意当 harness owner（这套东西需要有人养）
- 需求形态是"每天换一个方向"，几乎没有可复用的流程
- 只有一个 CLI、一个模型、一个人 —— 那你只需要规则文件，不需要 agent 编队

**最后一条值得单独说**：单人单模型时，`AGENTS.md` + `.ai/rules/` + 一个 verify hook 就够了，
11 个 agent 的编排成本大于收益。多人才是这套体系的前提，不是附加条件。
