# 审核与通知自动化接入指南

> 对应需求：`docs/01-requirements/RS-审核与通知自动化.md`。
> 三件东西：`harness.rules.json`（路由规则）＋ `scripts/review-router.mjs` / `scripts/ai-review.mjs`（审核自动化）＋ `scripts/lib/notify.mjs` / `scripts/harness-broker.mjs`（通知自动化）。
> 设计原则：机器能判的不用 AI；AI 是票拟，批红归角色；一切失败 fail-closed，绝不静默放行。

## 一、审核自动化：MR 触发 → 自动路由 → 审核 → 🔴 挡合入

`.gitlab-ci.yml` 接线样例（按类型分 job，`rules:changes` 防无关 push 重跑烧 token）：

```yaml
review:route:
  rules: [{ if: '$CI_PIPELINE_SOURCE == "merge_request_event"' }]
  script: node scripts/review-router.mjs --base "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"

review:rs:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      changes: ["docs/01-requirements/**", ".ai/tasks/*/rs.md"]
  script: node scripts/ai-review.mjs --type rs --base "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"

review:cr:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      changes: ["backend/**", "frontend/src/**"]   # 与 harness.rules.json 的 cr 路径保持一致
  script: node scripts/ai-review.mjs --type cr --base "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
```

退出码即门禁：`0` 通过；`1` 有 🔴（pipeline 红 → GitLab 合入规则挡住）；`2` 基础设施失败（同样红，绝不放行）。审核结论双落账：`.ai/reviews/<type>-<commit>.md`（入库，CI 可对账）＋ MR 嵌线（人读）。

### 必配 env（CI/CD 变量，masked）

| 变量 | 作用 |
|---|---|
| `AI_REVIEW_BASE_URL` | OpenAI 兼容端点（GLM/OpenAI/DeepSeek/自建网关均可） |
| `AI_REVIEW_API_KEY` | 模型凭据（只给审核用，不给 push 权） |
| `AI_REVIEW_MODEL` | 缺省模型；`harness.rules.json` 的 `model_tiers.narrow/deep` 可分档覆盖 |

### 省 token 的五个已内置机制

1. **L0 机器判据零 token**：RS 缺章节、无 Given/When/Then、ADR 引用不存在的 commit/路径——脚本先判，🔴 直接出，模型都不用调。
2. **L1 预打包**：清单前缀（静态，吃 API prompt cache）＋变更文件硬顶（`bundle.max_files=12`、`max_lines_per_file=600`，超限截断并在结论注明）。
3. **增量缓存**：同文件未变更沿用上轮结论，不重复调模型（`.ai/reviews/.cache-<type>.json`）。
4. **输出封顶**：findings 上限 `max_findings`，红优先保留。
5. **计量落账**：每次运行的 token 用量进 `.ai/ledger/events.jsonl`（`ledger:report` 可复盘哪类审核最烧钱）。

## 二、通知自动化：broker（票拟找人）

broker 是**薄事件桥**：不写 state、不跑 agent、不合 MR；一切落账走 GitLab 文件 API 的正式提交。

```bash
# HOST 默认 127.0.0.1：只绑回环，外部 webhook 打不进来。要接回调必须显式设 0.0.0.0。
# FEISHU_VERIFY_TOKEN 是飞书应用的 Verification Token，缺它则决策回投直接 503（见「安全边界」）。
HOST=0.0.0.0 \
GITLAB_WEBHOOK_SECRET=xxx GITLAB_URL=https://gitlab.example.com GITLAB_TOKEN=bot-token \
FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/xxx \
FEISHU_VERIFY_TOKEN=xxx \
FEISHU_NAME_MAP='{"ou_xxx":"张三"}' GITLAB_DEFAULT_BRANCH=main \
node scripts/harness-broker.mjs --port 8788
```

GitLab 侧：项目 → Webhooks → 填 `http://<host>:8788/webhook/gitlab`，secret 同上，勾 Merge request + Pipeline 事件。
飞书侧：卡片回调地址配 `http://<host>:8788/webhook/feishu`。登记地址时飞书会先打一次
`url_verification`，broker 会把 `challenge` 原样回显——不回显的话地址根本配不上。

### 事件流

| 事件 | 行为 |
|---|---|
| MR open/reopen | 拉 diffs → 按 rules 路由 → 卡片列出命中的审核与**批红角色** |
| diffs 接口失败 | 通知降级送达（fail-open，卡片注明），审核本体不受影响 |
| pipeline failed | 卡片找**作者**（不刷全员） |
| 其他事件 | 只进 digest 日志，不推卡片（防通知疲劳） |
| 决策卡片点选 | 以批红人身份把结论写进 RS「开放问题」表（GitLab 提交，commit message 带身份）；账实不符（OP 行不存在）显式 422，不盲写 |

### 安全边界

- **两个入口两套鉴权，都不能省**：GitLab 侧 `x-gitlab-token`（不匹配 403）；飞书侧 `body.token`
  对比 `FEISHU_VERIFY_TOKEN`（不匹配 403，**未配置则 503 拒服务**）。
  读路径可以试点裸奔，写路径不行：回投是唯一会改仓库的动作，而 `operator.open_id` 是调用方给的，
  不验签就等于允许任何人以任意人的名义批红。
- bot token 只需 `api` 读 + 文件写权限；**不给**合 MR、不给 push 保护分支。
- 决策回投只改 RS 文档的 OP 行；state.json 一律不碰（OP-1 的正式方案见 RS 开放问题表）。
- `HOST` 非回环且两个 token 没配齐时，启动日志会显式告警——绑 0.0.0.0 而不配 token
  等于把回投入口挂到公网。

### 内网部署：入站改走长连接（`FEISHU_MODE=ws`）

GitLab 在内网、飞书在公网时，**出站全通、入站只有一半断**：卡片发得出去（broker → 飞书 webhook），
但按钮回调进来不了（飞书 → broker 需要一个公网可达的地址）。长连接把这条线反过来拉：
broker 主动向飞书网关建一条 WebSocket，事件顺着这条已建好的连接推下来，不需要公网 IP、
不需要为飞书开放入站端口。

注意它只免掉**飞书那一条边**：`GitLab → broker` 的 webhook 仍然要打到 broker。
GitLab 与 broker 不同机时 `HOST` 仍需绑内网地址（`0.0.0.0` 或本机内网 IP），
绑回环就收不到 MR 事件——这条常被"内网不用开端口"这句话轻轻带过。

```bash
# 与上面唯一的差别：入站方式声明为 ws，并给应用凭据（长连接是用它们换来的）
# HOST 仍按 GitLab 能不能打到 broker 来定；飞书那一侧不再需要公网入口。
HOST=0.0.0.0 \
GITLAB_WEBHOOK_SECRET=xxx GITLAB_URL=http://gitlab.internal GITLAB_TOKEN=bot-token \
FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/xxx \
FEISHU_MODE=ws FEISHU_APP_ID=cli_xxx FEISHU_APP_SECRET=xxx \
FEISHU_NAME_MAP='{"ou_xxx":"张三"}' \
node scripts/harness-broker.mjs --port 8788
# 启动会打印 FEISHU_MODE ws —— 运维靠这一行确认"入站到底怎么接的"
# 探活：curl /healthz 能读出 feishu.connected —— 进程活着不等于通道还活着
```

飞书后台：开发者后台 →「事件与回调」→ 订阅方式选**长连接**。这一步和填回调地址是**互斥**的，
配了长连接就别再指望 `/webhook/feishu` 收到东西（反之亦然）。两种方式只认一种，所以 broker
要求显式声明 `FEISHU_MODE`；缺凭据直接 exit 64 拒启动，拼错取值也拒（不猜、不静默回退）。

| 模式 | 入站鉴权载体 | 适用 |
|---|---|---|
| `http`（缺省无凭据时） | `FEISHU_VERIFY_TOKEN` 对比 `body.token`，未配置 → 503 | broker 有公网入口，或同机反代 |
| `ws` | 通道本身：连接用 AppID/AppSecret 换来，只有飞书网关能往上推帧 | 纯内网；`FEISHU_VERIFY_TOKEN` 不需要 |

长连接这条链上有三个坑，每一个都表现为"看着通了、账不对"：

1. **分片**：事件超过 2MB 会被网关拆成多帧（`sum`/`seq` 头），漏合并 = 事件体截断。
2. **重投**：断线重连后网关会重投"已收到但没来得及应答"的事件，不去重就是**同一份批红提交两次**。
   但去重只能在**处理成功之后**才记账——第一次因 GitLab 5xx 失败、应答 500 请求重投，
   重投却被自己当"重复"丢掉并回 200，飞书以为处理完了、账上却什么都没有。所以应答码就是开关：
   **可重试故障（GitLab 5xx / 网络）→ 应答 500，等网关重投；账实不符（OP 行不存在）→ 4xx + toast，不重投。**
3. **自签证书**：内网 GitLab 若是企业 CA，`NODE_EXTRA_CA_CERTS=/path/ca.pem`。
   它不会报错反而更危险：`mrFiles()` 里 `catch` 返回 null，卡片照发、只是不列 diffs。

### 更省的一条路：决策走 git，飞书侧零回调配置

长连接仍然要「broker 能 443 出站 + 代理放行 WebSocket」。如果连这个都不成立（只能走 HTTP 正向代理、或合规要求所有入站过 DMZ），
还有一条更省的路：**根本不要「飞书 → broker」这条边**。

做法是把手上的动作从"点卡片按钮"换成"改文档"：

1. 卡片按钮不再回传，直接跳转到 GitLab 的 RS 编辑页（`<GITLAB_URL>/-/edit/<branch>/<rs_path>`）；
2. 人把「开放问题」里那一行的状态改成 `已裁决：A` 并提交；
3. broker 从 **push 事件**里读这次 diff，落账（`decision_landed`，`via: "git"`）。

它只用到「GitLab → broker」这一条边——内网里唯一天然可达的那条。收益不止是省配置：

| | 飞书按钮回传 | 决策走 git |
|---|---|---|
| 需要的入站边 | 飞书 → broker（长连接或公网回调） | 无（只借 GitLab → broker） |
| 飞书后台配置 | 应用 + 机器人 + 回调 + 发版 | **只要一个群机器人 webhook** |
| 身份来源 | `operator.open_id`，**请求体声明**，谁有 token 都能冒充 | commit author，**Git 服务器记录**，客户端伪造不了 |
| 审计 | 账本日志 | `git log -p`，谁什么时候把哪行改成什么，一查到底 |
| 代价 | 点一下就走 | 多两步：点链接、改一格、提交 |

```bash
# 发卡机（或 broker）侧：声明走 link 形态
HARNESS_DECISION_MODE=link GITLAB_URL=http://gitlab.internal \
  node scripts/lib/notify.mjs --event decision.json --webhook "$FEISHU_WEBHOOK_URL"
```

broker 侧只需要一条配置（`harness.rules.json`）：

```json
"notify": {
  "git_decision": { "enabled": true, "approvers": [] }
}
```

- `approvers` 为空 = 不设名单，依赖 GitLab 分支保护（能 push 到默认分支的人本就有权批）。
- 配了邮箱就是 **fail-closed**：名单外的人改了只记 `decision_rejected`，不落账。
- 只认三个条件，多一个都算误判：**默认分支**（feature 分支上的改动还没生效）、**markdown 文件**、
  **状态列被改成「已裁决：X」的新增行**（`-` 行是作废的旧值，认它等于把改判前的结论又落一次账）。

这条路 broker **不写仓库**——commit 本身就是账。所以重复推送最多多一条日志，不会造成账实不符；
读不到 diff 时记 `decision_landed_failed` 而不是假装"这次没有决策"。

两条路可以并存，而且应该并存：长连接给你"点一下就落账"的体验，git 那条是它挂掉时的兜底
（`/healthz` 里 `feishu.connected=false` 时，人照样能在 GitLab 上批，账照样落）。闭环不该押在一条边上。

#### 上真 GitLab 验一遍（L2）

mock 只能证明"按我理解的 GitLab 行为，逻辑是对的"；真实例才能证明"这个理解本身对不对"。
本地起一套（arm64 自建镜像，不动项目里任何东西）：

```bash
gitlab-arm64/run-harness-gitlab.sh     # http://127.0.0.1:8929（root 密码见脚本）
npm run e2e                            # 43 条断言，约 4 分钟；环境没起来时退出码 78
```

L2 不进 `npm run gate`（要 docker、要几分钟）；它守的是"假设"，L1 守的是"逻辑"——
所以 L2 抓到的每个问题，都要在 L1 里补一条能红的用例，否则下次改坏没人知道。

在真实例上跑通的第一个版本，暴露了四个只有真实环境才现形的问题：

| 现象 | 真因 | 处理 |
|---|---|---|
| 建 webhook 报 `Invalid url given` | 实例默认**不放行**内网请求 | 开 `allow_local_requests_from_web_hooks_and_services`；broker 就在内网，这是必踩 |
| 收得到事件、回 200，但一封没落账 | `GITLAB_TOKEN` 填了 OAuth access token，而 broker 用 `private-token` 头（只认 PAT）→ 全部 401 | 用 PAT；broker 启动时探一次令牌，不可用直接报警 |
| Developer 合并 MR 返回 **401** | 默认分支保护里 merge 也要 Maintainer（不是 403，容易误判成认证问题） | 调 `merge_access_level`，或用 Maintainer 身份合 |
| 一次合并落**两条账**，还记成两个人批的 | push 里既有原提交又有合并提交；合并提交的 diff 相对第一父就是整条分支的净变更 | 按 `blocker` 跨 commit 去重：同结论保留首次出现的身份，改判取最后一次 |

最后一条是这条路最贵的坑：账本看起来"两个人批了同一个问题"，审计一追就是账实不符。
它也解释了为什么 `approvers` 名单要按 **commit author** 判——合并提交的 author 是合并者，
不是真正动文档的人。


## 三、调整路由 = 改数据不改代码

所有路径模式、判据、模型档、批红角色都在 `harness.rules.json`：新仓库改 `reviews.cr.paths_from` 的 projects 槽（`harness.config.json`）；新增审核类型加一段 `reviews.<id>`，`machine_checks[].id` 必须命中 `scripts/lib/review-checks.mjs` 注册表（未知 id 直接 exit 2，不静默跳过）。

## 四、常见问题

- **本地试跑不烧钱**：`node scripts/ai-review.mjs --type rs --dry-run ...` 打印打包统计，0 次 API 调用。
- **没配模型 key**：机器判据有 🔴 仍会阻断（exit 1）；判据干净则 exit 2——缺凭据得不出结论，拒绝装作通过。
- **`--machine-only`**：只跑 L0 判据的显式降级（例如内网审核禁用外部模型时）。
  **配了 key 也不调模型**——它的全部意义就是"这次不花钱"，所以判断顺序排在"有没有凭据"之前。
  同理，机器判据已经出 🔴 时也不再调模型：AI 再多说什么都改不了退出码，只多一笔 token。
- **换机器/换包之后先验一遍装出来能不能用**：`harness.rules.json` 是审核自动化的唯一数据源，
  它必须随包发布（`package.json` 的 `files`）。init 现在对"声明了但包里没有"的模板文件直接报错，
  不再静默跳过——以前的表现是 install 绿灯、第一次跑 router 才 exit 2。
- **卡片点了没反应**，按这三条顺序查：① 后台订阅方式与 `FEISHU_MODE` 是否一致（长连接 vs 回调地址互斥）；
  ② 启动日志那行 `FEISHU_MODE` 是不是你以为的那个；③ `.ai/ledger/events.jsonl` 里有没有
  `decision_rejected` / `decision_writeback_failed`——点了却无记录，说明事件根本没到 broker，问题在入站；
  有 `decision_writeback_failed` 则是到了但没落账，看 `retryable`。
- **决策卡目前要显式投递**：`node scripts/lib/notify.mjs --event <json> --webhook <url>`。
  自动触发点（MR 路由出 🔴 时随路由卡片附一张决策卡）还没接，别以为它会自己发。
