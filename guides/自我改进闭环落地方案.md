# 自我改进闭环落地方案

> 背景：分析 NousResearch/hermes-agent 的 self-improving 机制后，针对本仓库现状给出的嫁接方案。
> 原则：用 harness 自己的哲学嫁接——**规则即代码、机器可验收、门禁 fail-closed / 观测 fail-open**。
> 本文只新增机制，不改变现有门禁语义。

---

## 0 现状诊断：闭环五环，已有两环半

自我改进闭环 = **信号采集 → 学习推理 → 提案 → 审批执行 → 效果验证**。

| 环 | 现状 | 已有设施 |
|---|---|---|
| 信号采集 | ✅ 比 hermes 更好 | deny ledger（拦截观测含 target 基线）、`state.json`（阶段 fail/waived/回退）、`.ai/ledger/events.jsonl`。hermes 靠 turn replay 主观判断，我们靠机器裁决客观数据 |
| 学习推理 | ✅ | `retro-ledger` agent：数据来自 state.json、四类根因、停点质量、"无沉淀 3 次改复盘"元规则 |
| 提案 | ⚠️ 半成品 | RETRO 模板 §4 是 markdown 勾选框，**机器不可读**，没有下游消费者 |
| 审批执行 | ❌ 断点 | 审批基础设施齐全（approval_role / 飞书卡片 / git 决策方案 D / guard_write 写域），但**没接到 skill 修订上** |
| 效果验证 | ❌ 断点 | 数据都在，没有"沉淀生效前后 fail 率对比"的聚合出口 |

`retro/` 目录为空不是没人复盘，是复盘产出没有去处。

## 1 设计映射表（hermes → harness-starter）

| hermes 机制 | 我们的等价物 | 动作 |
|---|---|---|
| review fork（turn 后触发） | retro-ledger（任务关闭触发） | 触发密度不照搬：任务级触发已合适，见 §5 |
| skill_manage 工具 | **新增**提案通道 | P0：提案 JSON；P1：propose-apply 脚本 |
| write_approval（staged write） | MR 本身 | P1：提案→branch→diff→MR，merge 即 apply。**git 就是审批队列**，复用方案 D 哲学，不新增回调面 |
| read-before-write（强制重读） | **机器化强于 hermes** | P0：提案里 old 段必须与磁盘当前内容逐字匹配，否则 proposal-check 拒绝 |
| .usage.json 使用遥测 | resolve-skills 加载点 | P2：加载即记账 |
| curator 生命周期（stale/archive） | ledger-report 扩展 | P2：只报告不自动归档（团队库变化须可预期） |
| review 提示词负面清单 | retro-ledger 硬规则补充 | P0：见 §4 |
| 缓存奇偶性 fork / 便宜模型路由 | modelTiers narrow 档 | 已有，retro 已可用窄模型 |
| MEMORY.md / USER.md | **不搬** | 开发 harness 无个人画像语义；团队记忆就是 `.skills/` + `harness.rules.json`，见 §5 |

## 2 P0 — 提案结构化（半天）

**目标**：retro 的"沉淀决策"从勾选框变成机器可读、机器可校验的工件。

### 2.1 新增 `.ai/proposals/<YYYY-MM-DD>-<slug>.json`

```jsonc
{
  "schema_version": 1,
  "task": "my-feature",
  "root_cause": "gate_not_executable",       // 四类根因之一，与 RETRO 模板 §2 对齐
  "type": "revise_skill",                     // revise_skill | new_skill | revise_rule | no_op
  "target": ".skills/backend/SKILL.md",       // revise_* 必填；new_skill 为新建路径
  "section": "## Pitfalls",                   // 可选，定位到节
  "patch": { "old": "<逐字原文>", "new": "<替换文>" },  // revise_* 必填
  "rationale": "一条规则 + 一句为什么（机制），非事故叙述",
  "evidence": ["deny.jsonl#2026-11-03...", ".ai/tasks/my-feature/state.json#stage:cr"],
  "no_op_reason": null                        // type=no_op 时必填；连续 3 条 no_op 触发复盘自查
}
```

### 2.2 新增 `scripts/proposal-check.mjs`

校验链（全部机器裁决，对应 evidence review 的"不走 AI"哲学）：

1. schema 完整性；
2. **read-before-write**：`patch.old` 与磁盘当前内容逐字匹配（不匹配 = 基于过期内容提案，拒绝。hermes 靠提示词约束，我们靠字节比对，更强）；
3. evidence 引用的账本行真实存在；
4. `type=no_op` 时 `no_op_reason` 非空。

退出码语义与现有脚本一致（0 通过 / 1 校验失败）。加入 `npm run gate`。

### 2.3 改动面

- `templates/RETRO-复盘.md` §4：勾选框旁注明"沉淀决策需同步产出 `.ai/proposals/*.json`，proposal-check 通过是复盘退出条件"；
- `agents/retro-ledger.agent.md`：`writes` 增加 `.ai/proposals/**`；退出条件补一条；硬规则补 §4 负面清单；
- `guard_write` 写域：`.ai/proposals/**` 允许 retro-ledger 写。

## 3 P1 — 审批执行链（1–2 天，全部复用现有件）

**目标**：提案自动变成"人只看 diff、机器管其余"的 MR 流。

```
.ai/proposals/x.json
   │ scripts/propose-apply.mjs
   │   1. proposal-check 通过
   │   2. git checkout -b retro/<date>-<slug>
   │   3. 应用 patch → commit（message 带提案路径与 evidence 摘要）
   │   4. push + 开 MR（approval_role 取 harness.rules.json 对应位，默认 tech_lead）
   │   5. 调 harness-broker 发飞书卡片（复用 card_events.decision_open）
   ▼
人审 MR（看 unified diff——这就是 write_approval 的 staged write）
   │ merge = apply；close = 拒绝（提案 JSON 留档，retro 可引用"被拒提案"）
   ▼
CI：check:skills + gate + npm test 全绿才可 merge
   │ （skill 修订本身过门禁——学习产物也机器验收）
   ▼
session_start 下个会话自然加载新 .skills/（无需任何刷新机制）
```

关键设计决策：

- **MR 就是审批队列**。不建 `/skills approve` 命令、不加飞书回调——方案 D 已证明"git 即决策"是内网最省边的路径，skill 修订走同一条边。
- **`.skills/**` 与 `harness.rules.json` 收进受控写域**：guard_write 只放行 propose-apply 脚本（workflow 标记），agent 运行时**不可**直接改技能与规则——比 hermes 的 write_approval 默认关更严。经验只能走"提案→MR"单行道。
- propose-apply 幂等：提案已被应用（MR 已存在/已 merge）时退出码 0 并打印状态，不重复开 MR。

## 4 防退化——retro-ledger 硬规则补充（照搬 hermes 的教训清单）

以下直接加进 `agents/retro-ledger.agent.md` 硬规则（这些是 hermes 用真实事故换来的清单）：

1. **环境性故障不沉淀**：缺二进制、装完即好的报错、路径不对——用户/运维能修，不是规则。
2. **工具负面断言不沉淀**："X 工具坏了 / 某命令不可用"会硬化成 agent 自我设限的引用，环境修复后还引用数月。要沉淀就沉淀"修复动作"（装什么、配什么）。
3. **未验证的死路不写成最佳实践**：试了几条路都没成功，禁止把失败序列包装成"推荐流程"。no_op 比 pseudoscience 好。
4. **一次性任务不新建 skill**：提案 type=new_skill 时，名字必须是类级（触发词 + Stage 0 清单已有要求；补禁 PR 号 / 日期 / 错误串命名）。
5. **一条教训只进一处**，路由规则：
   - 流程性经验（怎么做某类任务）→ `.skills/`
   - 机器可执行的约束（什么必须拦）→ `harness.rules.json` / 门禁
   - 纯观测（发生了什么）→ ledger，**永不**同时写两处。

## 5 P2 / P3 — 遥测与效果回环（各 1 天）

### P2 使用遥测 + stale 报告

- `resolve-skills.mjs`：每次命中技能时向 `.skills/.usage.json` 记 `{use_count, last_used_at, last_task}`（fail-open，记不上的不影响解析——观测不绑架主功能，同 deny ledger 边界）；
- `ledger-report.mjs` 扩展：LRU 技能榜 + 超 90 天未用清单，作为 retro-ledger 的输入之一；
- **不做自动归档**：团队共享库的结构变化必须走 MR、可预期。只出报告，归档是人工命令。

### P3 效果回环（harness 相对 hermes 的独有优势）

hermes 的学习效果只能靠人体感；我们有客观门禁数据，应该做实：

- 新增 `scripts/retro-metrics.mjs`：按月聚合 `state.json` 的（根因 × 阶段）fail 率与 deny 误拦率，关联提案——输出"该提案 merge 前后，同门禁 fail 率变化"；
- RETRO 模板 §1 加一行：**"上次相关沉淀生效了吗"**（数据引用 retro-metrics）；
- 这把"无新沉淀 3 次要改复盘"升级成有数据出口的元环：不仅问"学到了吗"，还问"学了管用吗"。

## 6 明确不搬的部分

| hermes 机制 | 不搬理由 |
|---|---|
| MEMORY.md / USER.md 个人记忆 | 开发协作无个人助理语义；团队记忆 = skills + rules，全部走 MR 治理 |
| 每 turn 后台 review fork | 触发密度错配：流水线的自然边界是任务关闭，不是 turn；任务级 retro 已够，且省掉 fork/缓存基建 |
| curator 自动 consolidation | 团队库的结构性合并必须人审；自动归档都不做，何况自动合并 |
| Skills Hub 生态接入 | 与本闭环正交，另行立项 |

---

## 7 分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| P0 | 提案 JSON + proposal-check + 模板/agent/guard 改动 | `gate` 含 proposal-check 自测；构造过期 old 的提案被拒 |
| P1 | propose-apply + MR 流 + 写域收紧 | 端到端：假提案→MR→merge→下个会话技能生效；agent 直改 .skills 被 guard 拦 |
| P2 | 使用遥测 + stale 报告 | ledger-report 输出 LRU 榜；遥测 fail-open 验证 |
| P3 | retro-metrics + 模板元环 | 能回答"某沉淀前后 fail 率" |

P0+P1 合计约 2–3 人日，即可把现有"两环半"补成完整闭环。
