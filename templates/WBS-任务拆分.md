# WBS-<需求标题>

> 产出：`feature-decomposer` · 写入 `state.todos` 并落盘 `docs/02-features/<module>/<slug>.wbs.md`
> 规则：叶子必须可独立验证；不按文件拆；每栈有且仅有一个统一验证 TODO。

## 1 拆分树

| id | 栈 | 任务 | 验收标准 | spec_ref | depends_on | 风险级 | required_skills |
|---|---|---|---|---|---|---|---|
| T1 | backend | | | `fs#§4.1@3b91d0` | — | HIGH | |
| T2 | frontend | | | `fs#§4.2@3b91d0` | T1 | MEDIUM | |
| V1 | backend | 统一验证：编译 + 定向测试 | 全绿零警告 | `fs#§4.1@3b91d0` | T1 | — | |

> `spec_ref` 的格式是 `fs#§<小节>@<blob7>`：小节指回 FS 的详细设计，blob7 是 FS 定稿那一刻的
> `git hash-object` 前 7 位。它回答的是「这条任务拆的是哪一版设计」。
>
> 为什么要这一列：任务与设计之间正常的失联方式是**没人发现**。FS 改过而 WBS 没回填，
> 任务指向的小节就不存在了（悬空任务，做出来没人要）；反过来 FS 写了却没任务，就是漏做，
> 交付前一周才发现。这两个方向都只有把引用写成机器可读的，才判得出来——
> `ci-verify` 的完备性检查就是比这张表与 FS 的小节集合。

## 2 依赖拓扑

```text
T1 ──→ T2 ──→ V1
 └───────────→ V2
```

> 无环是硬要求。出现环说明拆分粒度错了，回到 RS 重新看边界。

## 3 统一验证收口

| 栈 | 验证 TODO | 覆盖范围 | 命令 |
|---|---|---|---|
| backend | V1 | 本需求全部后端 TODO | `<test-cmd>` |
| frontend | V2 | 本需求全部前端 TODO | `<fe-test-cmd>` |

## 4 不作数的情况

- 叶子写成「改 A.java」——按文件拆，无法验证完成
- 叶子没有验收标准——无法判定 done
- `spec_ref` 留空，或指向 FS 里不存在的小节——这叫**悬空任务**：拆的时候 FS 还没有那一节，做完才发现没人要
- FS 有 §4.x 却没有任何任务对应——**漏做**，而且交付前不会有人发现
- 实现 TODO 自己跑全量测试——应由统一验证 TODO 收口
- 联调工作藏进某个实现 TODO——应单列，否则永远没人做
