# Apse 借鉴候选（retro 沉淀）

> 来源：外部系统复盘《Apse：从 Agent 循环到漏洞处理与挖掘》（TDengine，2026-11-07）。
> 已落地两项：checklist 第 37 条（停机在边界）、CR 模板验证阶梯教义段。以下为按价值排序的候选，
> 各条注明触发条件——到条件出现时再立项，不做预防性建设。

| # | 候选 | 触发条件（什么时候做） | 落点 |
|---|---|---|---|
| 1 | **认领原子性不变式**：「即将开始」的状态若不与认领动作同锁，会被并发执行者当成「已经开始」（Apse locate 抢跑）；对扫描器可见的任务必须字段完备（两步打标签教训） | broker 开始派发会话（规划 Phase 2）之前 | `.ai/locks/` 已有目录无纪律；写进 guides + orchestrator agent 定义 |
| 2 | **写后回读**：平台 API「返回成功但静默丢弃」是真实形态（Apse 飞书字段批量写丢 text 类），一切关键写操作 PUT 后回读验证 | broker 决策回投进生产（TDC 部署）时 | `resolveDecision` 尾部加一次 GET 比对 + 用例 |
| 3 | **决策证据包「一屏四块」**：变更/理由/验证证据/风险，≤1 屏——对"认知投降"（人保留批准权却没时间判断）的工程化缓解 | 决策卡片在团队实际使用两周后按反馈调 | `lib/notify.mjs` 渲染 + CR verdict 排版 |
| 4 | **批红龄期巡检**：等待人决策的项超过 N 小时主动催办——人在门口堵住，循环就断了 | broker 上线带 digest 时 | broker digest 加 Reviewing 龄期统计 |
| 5 | **落地四步**：影子（只读产报告）→单任务（人工触发）→小批（3-5 单看锁/字段）→定时+auto-adopt | TDC 部署 broker 的执行顺序 | guides/审核与通知自动化.md 部署节补顺序说明 |
| 6 | **定时巡检负载**：CI schedule 每晚全库 ai-review 巡检（对应 Apse 挖掘负载：无告警输入、自己找候选；门槛「只报能证实的，宁可不报」） | 审核自动化在 TDC 稳定运行一个月后 | gitlab CI schedule + rules 增 audit 类型 |
| 7 | **度量口径纪律**：报表每列标「事实/观察」，策略处置与失败分开计，测不了的明说 | ledger-report 下次增强时 | `ledger-report.mjs` 输出格式 |
| 8 | **预算三维**：任务级累计 token/usd + 墙钟（人等/外部等不计时）+ blocked TTL 自动回流程；停机判断在调度层 | 多 agent 并行长任务成为常态、出现过一次"任务永久卡住"之后 | state schema 加 budget 段（需 guard_state 认可，走正式立项） |

## 已对齐不重建（记录判断依据）

状态外置/制品交接（我们更强：git 入库）、门禁绑证据（差距：日志可加内容哈希）、人工边界四不做（合并/发布/打回裁定/拆批豁免——与我们批红哲学一致）、零成本查询不进 agent（L0 机器判据同构，Apse 有 $0.32 vs $3.5 的成本背书）、fail-closed（我们的 guard hooks 真拦截，Apse 安全边界仅在 prompt，此处我们更强）。

不照搬：tick/worker 常驻调度拓扑（与「GitLab CI 为触发器、git 为唯一序列化点、中台只当秘书」的设计决策相悖；借的是循环工程学，不是进程拓扑）。Apse workload.py 3745 行平台知识的教训，反证 harness.rules.json 数据化路线正确。
