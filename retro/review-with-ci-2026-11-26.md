# Retro — review-with-ci（2026-11-26）

## 一句话

!1847 有评审人 yqli 的打回评论，task-loop 却从未触发修复——根因是 `fetchTriggers` 请求 `/discussions` 不带 `per_page`，GitLab 默认每页 20 条，该 MR 有 22 条、打回评论落在第 2 页；runner 每轮看到的都是「无评审意见、CI 红」，走 CI 分支修了 10 轮后转 `needs_human`，工单里从未出现评审意见。修复 = discussions 翻页取全，取不全即抛错、不按部分结果判定。

## 教训

1. **「读到了」不等于「runner 读到了」——验证必须用被测对象的实际请求方式。** 诊断时我用 `?per_page=100` 读到了评论，于是认定「评论在、但被 CI 分支丢了」，并据此写了三处修复。实际上 runner 的请求不带 `per_page`，它从没读到过这条评论。那三处修复解决的是我从错误前提推出的假问题。教训的具体形态：**用自己的探测脚本得出结论前，先让探测脚本的请求与被测代码的请求逐字段相同**（此处差一个查询参数）。

2. **写防御代码前先确认它能被执行到。** 我加的「CI 红时带上评审评论」触发条件是「存在带结论词的评论」，而带结论词的评论在粗筛阶段就会被判成评审形态、根本走不到 CI 分支。这段代码找不到能执行到的场景。判别方法很简单却没做：**把触发条件代入上游的分流逻辑，看这条路径是否可达**。

3. **变异检验暴露「修了但没钉住」。** 审阅者指出「翻页出错后的分类零覆盖」，我补了用例并改了分类；再跑变异，M7（放行过宽到任何 404）与 M9（非数组响应退回空页）不红——代码改了、测试没跟上。**每改一处判定，同批补的用例必须能对这处判定变红**，否则下一次重构就会被无声改回。

4. **「改了」不等于「生效了」。** 针对审阅者 🟡#2（2xx 但非数组被当空页），我加了 `if (!Array.isArray(rows)) throw`，并报告已修复。实际 `res.json()` 对 HTML 先抛 SyntaxError，这段检查永远执行不到——行为碰巧是对的（致命退出），但修复本身是死代码。直到 M9 变异不红、再写探针复现才发现。**修复要以「变异后变红」或「探针复现」为准，不以「代码已写入」为准。**

5. **断言里出现的事件名必须真实存在。** 我在断言里写了 `!types.includes("claim_released")`，而这个事件名在代码里不存在——断言恒真。改用远端 `claims/mr-<iid>` 引用这个物理事实核对。**否定式断言尤其危险：拼错的名字永远「不包含」。**

6. **两处操作失误（已无损失，但过程有风险）：**
   - 变异脚本里误用 `git checkout <file>` 还原，清掉了该文件未提交的改动。变异一律用「先备份到 /tmp、改、cp 回」，不碰 git 状态。
   - 多次用「整行相等」作替换断言，因行内特殊字符反复失败（文件未被写入，是安全的失败）。定位锚点用**唯一子串**并先校验 `count==1`，再整体写入，避免半写。
   - 新增用例沿用了存量用例的命名（`5g-ter` 编号、`$TMP/e2e5gt` 目录、`ledger5gt` 账本、`e2e5gt.txt` 输出全撞）。共用账本导致两条用例的事件流串扰——审阅者做 M10b 变异时，存量用例 `--mr 过滤轮不动账` 被误判变红，排查后才发现。**与之前 todo id 撞名是同一类错误，这是第二次：新增任何具名资源（id、目录、账本、输出文件）前先 grep 查重。**

7. **抛错后的分类要写进设计，不能只在注释里说「抛错」。** 初版注释写「不为一个 MR 拖死全部」，实际 discussions 404 会走 `die(1)`、每 30 分钟崩一次并把剖面 B 一起拖死——注释与行为相反。定案：HTTP 404/429/5xx/超时 → 源级软失败（视角不完整、账目不动、下 tick 重试）；超页数上限、响应体非 JSON/非数组 → 致命（数据或接口超出设计，需要人看见）。放行只限 discussions 路径的 404：401/403 与其它路径的 404 仍致命。

8. **结论对、论据错，也要改。** 为「超页保持致命」我给的理由是「软失败是静默的，没人会看」。审阅者实跑后指出：软失败与 `die` 走同一条健康记分通道，连续失败都会触发 `loop_degraded` 与本地通知，退出码同为 1——「静默」不成立。真正的差别只有两点：`die` 连带拖停飞书源；软失败的「临时不可达」文案会把永久故障说成临时。结论没变，但如果没人实跑核对，一个错误论据会被后人当作设计依据继承下去。**给别人看的理由，要和代码一样经得起验证。**

9. **变异「不红」要先排除变异没生效——但归因前也要核实别人的变异。** 这一条经历了两次修正，两次都值得记：
   - 第一次：审阅者报 M11（软失败轮改写工单）不红。真实原因是**我的断言缺口**——工单只断言了 `existsSync`，改写了内容也看不出来。审阅者的变异是有效的。
   - 第二次：我自己复跑 M11 也不红，排查后发现**我的复跑脚本**用了硬编码相对路径 `.ai/task-loop`，runner 的 cwd 不一定是仓库根，工单根本没被改写——这次才是变异空转。
   - 我在 retro 初稿里把第二次的原因写成了第一次的解释（「审阅者报的不红是假绿」），审阅者核对后指出归因错误。**同一个现象（不红）在两次里原因不同**：一次是测试缺口，一次是变异空转。把它们的因果混在一起，等于把别人抓到的真问题说成不存在。
   - 操作教训不变：判变异结果前，先证明被测代码确实处于变异态（探针、哈希、目标行核对）；**说别人的结论错了之前，先复现对方的具体操作**。

10. **语法合法 ≠ 语义正确，`node --check` 对此无感。** 变异脚本的一个引号转义错误把 `if (...) break;` 写成了字符串字面量 `'      break;'`——合法的表达式语句，语法检查通过，但循环体里没有 `break`、`page` 不再推进判断，翻页变成死循环，测试套件挂住 5 分钟。差点被当成「已还原」继续提交。教训具体到操作：**还原后不只校验命令返回，要校验文件字节（`cmp`）；变异脚本也是代码，同样需要防护。**

## 沉淀决策

- **部分视角 = 拒绝判定。** 触发源的任何「取不全」（分页到上限、中途 HTTP 错、响应体形状不对）都必须让本轮视角标记为不完整，不允许基于已取到的部分下结论。下游 `gitlabViewComplete=false` 时 sweep 整体不动账。
- **不逐 MR 吞错。** 在 `fetchTriggers` 里跳过出错的单个 MR，等于让它从本轮视角消失，sweep 会把它的账目当「触发消失」关掉——比整轮失败更糟。
- **回退了四处防御性改动**（CI 分支带评论、CI 形态指纹叠加评论 id、评论并入 ack 清单、评论不受 CI 轮次上限拦截）：它们依赖「CI 红且有普通评论」这个找不到真实例子的形态，且变异不红（零覆盖）。留下的缺口如实记录：「CI 红且有人留了不带结论词的普通评论」时评论不进工单——存量行为，非本次引入，遇到真实形态再按实处理。

## 停点质量

- 真正的停点只有一次：向用户确认「补用例还是回退」。推荐了回退并说明理由，用户采纳。这次停点是必要的——两类方案的差别在于「要不要为推测场景维护代码」，这是判断而非事实。
- 错误归因更正了一次：最初报告「三处叠加」，核实用 runner 的请求方式后更正为「只有分页是病因」。更正在动手大改之前完成，损失限于时间。
