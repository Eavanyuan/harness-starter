# crewAI 借鉴候选（retro 沉淀）

> 来源：<https://github.com/crewAIInc/crewAI>，v1.15.39（2026-11-09 发版，60.7k star），
> 2026-11-10 读 GitHub API 树 + 核心模块源码（skills/ events/ hooks/ tasks/ memory/ flow/ experimental/evaluation/），
> 未跑其测试，结论限于代码形态。
> 结论先行：**它与我们不是同类产品**——它是"编排 LLM 干活"的框架，我们是"约束 agent 干活"的护栏体系。
> 因此可借的是**判据工程**，不是它的执行器。

| # | 候选 | 触发条件（什么时候做） | 落点 |
|---|---|---|---|
| 1 | **台账配对不变式**：crewAI 的事件上下文有 `EventPairingError` / `StackDepthExceededError` / `MismatchBehavior`——start/end 事件必须成对，不成对当场抛错，而不是留一个孤儿事件在账上 | **现在**（T3 已有实证：认领落账后崩在 `budget`，`refs/heads/claims/mr-7` 残留、无对应 release 事件） | `scripts/ledger-report.mjs` 增加配对检查：`claimed↔released|abandoned`、`attempt_started↔attempt_finished`、`trigger_found↔terminal`；`task-loop.mjs` 崩路径必须写 `abandoned` 再退出 |
| 2 | **skill 渐进披露三级**：`METADATA`（仅 name+description）→ `INSTRUCTIONS`（正文）→ `RESOURCES`（scripts/references/assets 目录清单），发现时只到一级，用 `build_skill_catalog()` 给模型一张"还能加载什么"的清单，按需 `activate_skill()` | skill 数 ≥ 8，或单次 `--diff` 命中 ≥ 3 份时 | `scripts/resolve-skills.mjs` 增 `--catalog`（只出 name/description/命中文件），正文由调用方按需读 |
| 3 | **skill 加载入账**：`SkillDiscoveryStarted/Loaded/Activated/LoadFailed` 四类事件全落账，加载失败可见但不断流程 | 同 #2；或第一次出现"这次为什么没加载那份 skill"的争论 | `resolve-skills.mjs` 写 `.ai/ledger/events.jsonl`（`skill_resolved` / `skill_load_failed`） |
| 4 | **护栏必须可证伪**：crewAI 开源的 `HallucinationGuardrail` 是个 **`return True, raw` 的空护栏**（付费占位，只打 warning）。它把这个坑明写在 docstring 里，反而给了我们判据：**任何 guardrail 都要有一条"把它改成恒真必须变红"的变异测试** | **现在**（我们已有 T2 恒真断言史，这条是把纪律焊到判据上） | `test/` 增加 `guardrail-vacuity.test.sh`：遍历 `scripts/lib/*guard*`、`hooks/` 判据，逐个短路后必须至少一条断言变红 |
| 5 | **护栏返回结构 (bool, feedback) 且异常即否**：`LLMGuardrail` 校验失败返回 `(False, 具体哪里不合规)`，feedback 回给 agent 下一轮；任何异常一律 `(False, ...)`，不 fail-open | T3 的 REWORK 分支真正接上修复子循环时 | `task-loop-core.mjs` 的 `approvalValid` 已对齐"缺数据按不通过"，扩成统一 `verdict(ok, reason)` 结构 |
| 6 | **不可判定返回 null，不给默认分**：评估指标的 `EvaluationScore(score=None, feedback=...)` 用于"没有工具可用"这类不适用场景，而不是塞个 5.0 蒙过去 | T5 影子周出第一版度量报表时 | `ledger-report.mjs` 的度量列允许 `null` 并标注"不可判定"，禁止用 0/均值填坑 |
| 7 | **hook 执行域（scoped hooks）**：全局队列 + 用 `contextvars` 挂的**执行域局部**队列，派发顺序全局先、局部后；`HookAborted` 是显式契约而非退出码约定 | runner 真跑通、需要"本轮临时收紧/放宽某条规则"时 | `.zcode/config.json` 增 `scope` 概念；`hooks/` 派发器支持一次会话内的临时覆盖 |
| 8 | **静态状态契约 + 图校验**：`Flow` 把状态声明成可序列化的定义（dict / pydantic / JSON Schema / unknown 四态），配置与持久化也序列化，因此**图可以离线校验**（死节点、无出口、环） | `state.json` 的 stage 数 > 8，或第一次出现"卡在某个 stage 出不去" | `ci-verify.mjs` 增：STAGE_CHAIN 每个 stage 都有可达出口、无孤儿 stage |

## 已对齐不重建（记录判断依据）

- **失败反馈回流**：crewAI 的 `(False, feedback)` → agent 重试，与我们的 REWORK + "已试过什么"同构（RS US-1 第 3 条）。
- **旁观者只读**：`EvaluationListener` 挂在事件总线上打分，不改流程——与 broker「只读事件、只发通知，不做第二状态源」同一裁决。
- **hook 真拦截**：crewAI 的 `HookAborted` 能中止调用；我们的 PreToolUse 退出码 2 同样真拦（Apse 那边只在 prompt 里写边界，我们更强）。
- **能力声明先于执行**：`allowed-tools` 在 skill frontmatter 里声明预批准工具，与我们 `applies_to` / `required_skills` 的"先声明后校验"同路。
- **名称去重 + 冲突消歧**：crewAI 用父目录名限定重名 skill；我们更严——`check-skills` 直接要求 `name == 目录名`，冲突不可能存在。

## 不照搬（含理由）

| 不抄的 | 理由 |
|---|---|
| 单文件巨型执行器（`agent_executor.py` 139KB、`flow/runtime/__init__.py` 164KB、`llm.py` 111KB） | 60k star 证明"能跑"与"可审"是两件事。我们的判据靠人读得完的脚本，体积即门槛 |
| LLM-as-judge 打分当门禁（0-10 分、threshold=8.0） | 打分不可复现、不可变异检验。我们只把它当**观察**（#6），闸门留给确定性判据 |
| `@org/name` skill registry 分发 | 引入信任链与版本漂移；我们已有 `upstream@sha` 锚，比 registry 更可审计 |
| 向量记忆（qdrant/lancedb，67 个 embeddings 文件） | 与"git 是唯一序列化点"直接冲突；记忆必须可 diff、可回滚 |
| 付费占位的空护栏 | 反面教材，见 #4 |
| 中央 scheduler / 常驻 worker 拓扑 | 与 ADR-010 D1「拉不推」冲突（Apse 复盘已裁过同一题） |

## 一句话方法论

**crewAI 把"多 agent 协作"做成了框架，把"agent 说得对不对"留给了付费产品。
我们反过来：不碰编排自由度，只做"凭什么信它"的判据。**
它的 `EventPairingError` 和 `score=None` 两个细节，比它 60k star 的编排能力对我们更有用——
因为那是把"不可信的中间状态"变成"当场报错的断言"。
