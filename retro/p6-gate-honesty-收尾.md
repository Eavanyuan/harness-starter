# p6-gate-honesty 收尾

基线 `11e07de`。三项修复，一条主线：**判据在执行面失真**。

## 1. 三条判据，三种失真

**A 放行条 —— 失真在时间维度。** 13 条全部 11-25 到期，而且 `7642f87` 已经把 11-13 续到 11-25。它没有"未处理"，它是**已经复发过一次**。机制里没有任何东西阻止第二次，所以第一次续期存在的意义就是让第二次变得自然。

修法不数次数（浅克隆会让它恒绿），改封窗口长度：到期日 − 授权日 ≤ 30 天。存量最长 26 天，判据上线即绿；第二次续期必然越界 → 红。

**B architect —— 失真在对象维度。** 两个 project 都指向 `../TDasset`，58.4s / 15.2%，32 红全是别人仓库的存量债，`--strict` 只拦新增所以永久豁免。这个坑更隐蔽的一层是：`test:architect` 带 `--root .`，看起来限定了范围，**但 `--root` 是根不是白名单**。名字在骗人。

**C gate —— 失真在机会维度。** 判据写对了、对象也没错，但它 383s 才跑一次，没人等，于是它等于不存在。CI 56s 的绿灯让"本地 6 分钟没人跑"这件事完全不可见。**判据不是在错误的答案上失败，是在没人跑到它的时候失败。**

## 2. 让"允许续期一次"变成"不允许续期"

这是 A 的核心判断。续期一次听起来无害，但它是复发的必要手段：允许一次续期 = 允许无限续期，因为第二次和第一次在机制上没有任何区别。要拦住复发，判据必须**让第二次续期成为异常**，而不是让第一次续期成为异常（那会把当下合法的状态也判红，然后被人整体关掉）。

30 天窗口正好卡在这条线上：第一次续期（11-13→11-25）是 23 天，合法；第二次（→12-25）是 53 天，红。

## 3. 跳过必须可见

B 的跳过如果静默，就等于用"没检查"冒充"检查通过"——这正是过去几轮反复出现的问题形态。所以跳过时打一行 `⏭ 跳过 2 个仓库外 project：backend(../TDasset), frontend(../TDasset)`。

顺带发现用 `dir` 去重会打出 `../TDasset, ../TDasset`（两个 project 同目录），改成 `id(dir)` 才看得出"跳过了两个 project"而不是"跳过了一个，重了"。

## 4. 并行的真正风险不是慢，是"少跑了但都是绿的"

并行最容易出的问题不是冲突，是**某段被跳过、整体仍绿**。所以做了两层验证：

- 执行器自测 7 条，其中最关键的一条是「中间段失败 → exit 1，而末段是成功的」。树形依赖（`a && b && c`）天然满足这条，并发聚合不天然满足。
- 逐套件核断言数：hooks 91、harness-cli 251、evidence 70、task-loop 150——串行与并行完全相同。只跑总时长不看断言数，就会漏掉"少跑一段"。

## 5. 并行把一个旧隐患挤了出来

`test/writes.test.sh` 一直在就地改写真实的 `write-allowlist.txt`，用 `cp -p` 备份 + `trap` 还原。串行时它只是"改完再改回来"，并行时它变成"全局状态的唯一写者"——正确性靠巧合维持。

而且它的注释里已经记着一个真实的代价：还原后 mtime 跳到"刚刚"，把声明了这个文件的 verify 证据判过期（DOCGATE-V1 反复变"过时"）。

改成 `HARNESS_ALLOWLIST` 指向副本后两个问题一起消失。**这条不是并行引入的，是并行让它从"能忍"变成"不能忍"。**

## 6. 教训

1. **判据的失效有四种形态**：算错（结果错）、看错对象（B）、看错时间（A/F5）、根本没跑到（C）。前两种靠变异验证能抓到，后两种要靠"它多久跑一次""它测的是谁"来问。
2. **`--root` / `--scope` / `--filter` 这类参数，名字必须能被误解成"限定范围"时，就得在输出里证明它限定了什么。** 否则"我加了 --root ."会变成一种自我安慰。
3. **允许一次例外 = 允许无限例外**，除非判据能把"第二次"和"第一次"分开。分不开的时候，只能把例外本身的窗口封顶。
4. **并行改造会放大所有隐式的全局状态依赖**。改之前先问"有几个写者"，而不是"跑一次是不是绿的"。
