## 1. A：放行条的有效期封顶

### 为什么不是「检查续期次数」

文件不记历史。数续期次数只能读 `git log -p`，而 CI 是浅克隆（`fetch-depth: 1`）——在 CI 上这个判据会**恒绿**。判据在浅克隆里假绿，比没有判据更坏：它给出一个"已检查"的假象。

改用文件自带的事实：**窗口长度** = 到期日 − 授权日。伪造不了，也不需要历史。

### 机制要害

`7642f87` 的提交信息写得很直白：「旧条目续期至 11-25」。它把 11-02 登记的条从 11-13 延到 11-25（23 天，仍在 30 天窗内）——**第一次续期合法**。第二次续期（比如延到 12-25）就是 53 天，红。

这就是设计意图：允许在一个窗口内调整一次，不允许无限往后推。允许续期一次的机制，等于允许永久续期。

### 改动

`hooks/write-allowlist.txt` 加第 4 字段（授权日），13 条按 git 首次入库日登记：

| 首次 | 到期 | 天数 | 条数 |
|---|---|---|---|
| 2026-10-30 | 11-25 | 26 | 1（guard_state） |
| 2026-11-02 | 11-25 | 23 | 5 |
| 2026-11-03 | 11-25 | 22 | 1（CR 模板） |
| 2026-11-10 | 11-25 | 15 | 2（package.json / quality-gate.yml） |
| 2026-11-11 | 11-25 | 14 | 3（shell / path_guards / glob） |

最长 26 天 ≤ 30，**这条判据上线即全绿**——它拦的是下一次续期，不是现在。

`scripts/doctor.mjs` 第 9 项：`到期日 − 授权日 > 30` → 阻塞。

### 变异证据

```
# 把 ledger.mjs 的到期日改到 2026-12-31（模拟第二次续期）
$ node scripts/doctor.mjs
  ✗ write-allowlist 放行条有效期超过 30 天：hooks/lib/ledger.mjs
    （2026-11-02 → 2026-12-31，59 天，:24）—— 续期只是在推迟判定。要么判定存废删行，
    要么把改动转成正式契约（ADR/代码注释），不要延长到期日
结果：1 个阻塞问题，4 个提醒。

# 还原后 md5 一致
```

## 2. B：architect 不再审别人的仓库

### 对象错位

`harness.config.json:288/297` 两个 project（backend / frontend）都指向 `../TDasset`，12G / 28.9 万文件。`architect` 28.4s + `test:architect` 30.0s，合计 **58.4s / 全量 15.2%**，产出 32 🔴 30 🟡——全是外部仓库的存量债，本地一条也修不了，而 `--strict` 只拦新增，于是永久豁免。

### 一个被名字骗了的地方

`test:architect` 的脚本是 `node scripts/architect-check.mjs --root .`。看起来限定了范围，但它照样扫外部——因为 `--root` 决定的是"根目录"，`projects[].dir` 是相对根目录的路径，`../TDasset` 完全合法。

**`--root` 是根，不是白名单。** 这条语义混淆让"我用了 --root . 所以只看自己"成了一个很自然的误解。

### 改动

`projects` 定义处过滤：`dir` 解析后落在 ROOT 外则跳过，`--include-external` 时不过滤。

跳过必须**可见**——这是本批的第一原则：

```
== F3 复杂度预算 ==
  ⏭ 跳过 2 个仓库外 project：backend(../TDasset), frontend(../TDasset)
    （外部仓库的存量债不归本仓库门禁管；需要时加 --include-external）
```

静默跳过与通过长得一样，那就等于没有判据。用 `id(dir)` 而不是纯 `dir`：两个 project 指向同一目录时会打出 `../TDasset, ../TDasset`，看不出跳过了几个。

### 改之前先核了「会不会引进新红」

清空/过滤 projects 有三处连带：`verify.mjs:1120`（todo.stack 合法性）、`check-skills.mjs:41`（stack 集合）、`verify.mjs:324`（证据链 sourceGlobs）。三处都是 `Array.isArray(projects) ? projects : stacks`，而 config **没有 `stacks` 键** → 空数组安全。实证：

- 存量 97 条 todo 的 `stack` **全部是 `harness`**，没有一条是 backend/frontend
- `check-skills:240` 只是少遍历两个 stack，不产生错误

### 结果

28.4s → **0.04s**，32 🔴 → 0 🔴。

## 3. C：34 段有界并发

### 为什么能并行

34 段无数据依赖，27 个测试套件全部 `mktemp` 自建夹具，无固定端口。实测 4 路 138.2s / 0 失败 / `git status` 前后无差异。

### 为什么不能无脑并行

`test:perf-checks` 的判据输入是**墙钟**：`sleep 1.0` 实测 ~1005ms，断言落在基线的 50~150% 区间。并发争抢把它推到 1.3s，"🟡 超五成"就变成"🔴 超一倍"——判据被环境打坏，不是代码变慢。

所以执行器把时间敏感段单独排队、独占跑。用白名单而不是黑名单：新增时间敏感套件忘了登记，只会让它被并发（可能假红）；用黑名单忘了登记，会让它被并发且**没人知道**。两种都不好，但前者会以"红了"的方式暴露自己。

### 执行器必须证明自己不吞失败

这是 C 的命门。串行的 `a && b && c` 在中间段失败时，bash 会停在那一句、退出码非零——行为是对的但"谁失败了"靠输出顺序。换成并发后，聚合全由执行器负责，写错就是"34 段里第 7 段红，整体 exit 0"。

`test/gate-parallel.test.sh` 7 条，逐条钉住：

| 断言 | 钉的是 |
|---|---|
| 三段全过 → 0 | 基态 |
| 中间段失败 → 1（**末段是成功的**） | 聚合不看最后一条命令 |
| 首段失败 → 1 | 不是只看末段 |
| 两段失败 → 两个报错块 | 不只报第一个 |
| 失败段的自有输出出现在日志尾部 | 可归因 |
| perf-checks 归入串行队列 | 时间敏感识别 |
| 空清单 → 2 | 配置缺失不当绿 |

### 断言数一致性（并行的隐蔽风险是"少跑了但都是绿的"）

逐套件串行 vs 并行核对：

| 套件 | 串行 | 并行 |
|---|---|---|
| test:hooks | 91 | 91 |
| test:harness-cli | 251 | 251 |
| test:evidence | 70 | 70 |
| test:task-loop | 150 | 150 |

### 顺带修掉一个并行隐患

`test/writes.test.sh` 原本**就地改写真实的 `write-allowlist.txt`**，靠 `cp -p` 备份 + `trap` 还原。两个代价（它自己的注释里记着第一个）：

1. 还原后 mtime 跳到"刚刚"，把声明了 `hooks/write-allowlist.txt` 的 verify 证据判成过期（实测 DOCGATE-V1 反复变"过时"）
2. 并行下"临时清空真文件"的窗口会被别的段看见，正确性依赖"碰巧只有一个写者"

改成 `HARNESS_ALLOWLIST` 指向 `$TMP` 副本后，真文件内容与 mtime 都不动，测试从"全局状态的唯一写者"变成完全隔离。验证：跑完 `md5` 与前一致。

### 结果

| 项 | 串行 | 并行 |
|---|---|---|
| 全量耗时 | 383s | **112s**（3.4×） |
| 段数 | 34 | 35（+gate-parallel 自测） |
| 失败 | 0 | 0 |

串行链保留为 `npm run gate:serial`——排查偶发红时，串行能排除并发干扰。
