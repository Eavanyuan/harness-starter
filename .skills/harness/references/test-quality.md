# 测试有效性：断言会不会骗人

> 参考：dotnet/skills 的 test-anti-patterns（MIT）与 auldsyababua 的 test-standards 的**判据分类**。
> 判据文字与命令是本仓库重写的，没有复制其原文，故未固定 commit——若日后直接引用原文，
> 必须改标「素材来源」并补 `@<sha7+>`（`check:skills` 会校验）。
>
> 未引入其附带的 python scanner：CI 镜像没有 python3，引进来就是重造
> 「工具缺失静默污染判据」那个坑。

**为什么单独写一份**：R7 只要求「改了行为必须同次补测试」，没说「补的测试会不会永远为真」。
这条空洞上周就应验了——三条用例本该拦住却全绿，根因是变异命令失败被 `>/dev/null 2>&1` 吞掉，
fixture 原封不动。**测试绿不等于代码对，也可能是测试没在测。**
本节覆盖三种形态：`test/*.sh`、Java（JUnit/AssertJ）、Vue（Vitest）。

---

## T1 无断言

**病灶**：测试把代码跑了一遍，什么都没检查。它证明的是「没抛异常」，不是「行为对」。

```bash
# Java：@Test 数量与断言数量严重不成比例
rg -c '@Test' --glob '*.java' . | head; rg -c 'assert|Assertions\.|verify\(' --glob '*.java' . | head
# Vitest：it/test 数量 vs expect 数量
rg -c '\b(it|test)\(' --glob '*.{ts,js,vue}' . ; rg -c '\bexpect\(' --glob '*.{ts,js,vue}' .
```

比例接近 1:1 才正常。差得远就逐个看——**不要看总数下结论**，去读那个 0 断言的文件。

## T2 恒真断言（最危险，因为它永远是绿的）

**病灶**：断言的值由测试自己刚设进去，或者条件永远成立。

```bash
rg -n 'assertTrue\(true\)|assertFalse\(false\)|expect\(true\)|expect\(1\)\.toBe\(1\)' --glob '*.{java,ts,js}'
rg -n 'catch[^}]*\{\s*Assert\.fail' --glob '*.java'
```

三种常见变体，grep 抓不全，必须人看：

- `assertThat(x).isEqualTo(x)` —— 跟自己比
- 先 `when(mock.foo()).thenReturn(1)` 再断言 `foo() == 1` —— 断言的是 mock 配置，不是被测代码
- 断言写在「一定会走到的分支」里，条件为假时不报错

> **`test/*.sh` 的特别说明**：`check "名称" "期望" "实际"` 里空期望是**合法**的
> （表示「期望输出为空」），不是恒真。判断标准是：期望值是不是从被测行为推出来的。

## T3 吞异常 / 吞失败

**病灶**：失败被 try/catch 吃掉，或者命令失败被 `|| true`、`2>/dev/null` 抹平。

```bash
# 空 catch
rg -n -U 'catch\s*\([^)]*\)\s*\{\s*\}' --glob '*.{java,ts,js}'
# 吞掉失败
rg -n '\|\|\s*true|2>/dev/null\s*$' test/
```

**这是本仓库踩过最狠的一次**：变异命令跑不起来 → 被 `>/dev/null 2>&1` 吞掉 → fixture 没变 →
「本该拦住」的用例变成恒真。现在的规矩是**变异失败必须当场判红**（见 `test/skills.test.sh` 的 `mut`）。

判据：`2>/dev/null` 用在「可选探测」可以（如 `2>/dev/null || true` 找可选命令），
用在「必须成功的准备步骤」就是缺陷——准备失败必须 `exit 1`，不能接着跑断言。

## T4 断言被注释掉

**病灶**：曾经红过，于是注释掉，测试继续绿，看起来还在覆盖。

```bash
rg -n '^\s*(//|#)\s*(assert|expect|check|verify)' --glob '*.{java,ts,js,sh}'
```

命中即问：为什么注释？如果是「行为改了」，就该删掉这条测试并说明；如果是「暂时不过」，
那是真 bug，不许留。

## T5 只有 happy path

**病灶**：只测成功路径，错误分支一条没有。上游叫 happy-path bias。

判据不是 grep，是**对照**：这个测试文件覆盖的公开方法，每个有没有至少一条失败用例
（非法入参 / 越权 / 并发冲突 / 外部依赖失败）？

最少要求：**新增的写接口必须有一条「非法输入被拒」的用例**。这条与 R2（入参校验）、
R9（越权校验）配套——校验写了却没测，等于没写。

## T6 非确定性

**病灶**：靠 sleep 同步、依赖真实时间/随机数/固定端口，本地绿、CI 红，或反过来。

```bash
rg -n 'Thread\.sleep|Task\.Delay|time\.Sleep|cy\.wait\(|setTimeout\(.*[0-9]{3,}' --glob '*.{java,ts,js}'
rg -n 'DateTime\.Now|LocalDateTime\.now\(\)|new Date\(\)|Math\.random' --glob '*.{java,ts,js}'
```

`now()` 与随机数不一定是缺陷，但**断言里用了它们**就是。判据：断言是否依赖「这次跑的具体值」。

## T7 变异检验（唯一能证明断言有效的办法）

前面六条都是静态的，只能找到**可疑**。要证明一条断言真的在测东西，只有一个办法：
**把它该抓的 bug 造出来，看它红不红。**

```
1. 改坏被测代码（一行就够：反转条件、删掉校验、把返回值改成常量）
2. 跑这条断言 → 必须是红的
3. 恢复代码 → 必须回到绿
4. 把「怎么变异的、红在哪」写进交付说明
```

**什么时候必做**：

- 新增断言
- 修改断言（尤其是放宽期望值）
- 修 bug 时补的回归测试

**为什么值得**：上周三个变异全部有效，才让「42/42 通过」这个结论有分量；
而更早那次「变异自己失败被吞掉」，正是因为没做第 2 步——看起来跑了变异，其实 fixture 没动。

> 这条不可自动执行（要改代码），所以它不进 CI，进 `/cr` 的必答项：
> **「本次新增/修改的断言，变异后是否红？」答不上来就是未交付。**

---

## 交付时怎么用

不是每次改代码都要跑完 T1–T7。按改动类型取：

| 本次改了什么 | 至少做 |
|---|---|
| 改了业务逻辑 + 补测试 | T7（变异）+ T5（失败路径有没有） |
| 只加测试、没改逻辑 | T1、T2、T4 |
| 修 flaky | T6 |
| 改 `test/*.sh` 本身 | T3（有没有吞失败）、T7 |

## 上游没抄的部分（明说）

- **不加 python scanner**。上游 `test_quality_scanner.py` 的判据已并入本文的 grep；
  引入脚本会让 CI 依赖多一个运行时，而那正是上周四个缺陷的共同成因。
- **不用它的 severity 分级**（Critical/High/Medium/Low）。本仓库用 🔴/🟡/ℹ️ 三级，
  两套分级并存只会让人在「这条算 Critical 还是 High」上耗时间。
- **不做「断言覆盖率」指标**。数量不等于质量——一条变异有效的断言，胜过十条恒真的。
