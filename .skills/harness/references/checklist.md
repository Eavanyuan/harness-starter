# 门禁失效点自查

这 37 条全部来自本仓库、同类项目或已发表外部系统（Apse）的真实故障，不是设想。
写新 hook、改判定条件、加规则之前逐条对一遍。

前 9 条是"判据坏了"，中间几条是"门禁根本没到场"，23–26 是"判定与呈现、观测脱节"
（分档只改显示、推进替门禁下结论、日志只写不读）——后者更危险，因为它通常还配着绿灯。
27–34 是"判据吃到了坏输入"：解析把数据位当空白、包装器吃掉自己的入参、
契约只查一个方向、规则没有用例、豁免比门禁更便宜、工具产出自己判红的状态、例外清单自授权、
用例只证有而不证无。
这一类的共同点是**代码看起来完全正常**，错在它读进来的东西。
35–36 是"判据的洞不表现为失败"：次序错了每步都合格、判据漏了命中只会输出绿灯。

## 1. 根路径多退/少退一层

hook 在 `hooks/` 下，`resolve(dirname, '..')` 是仓库根；写成 `'../..'` 就读不到 `harness.config.json`。
读不到配置时如果走了 `deny`，表现是**所有命令都被拦**；如果走了 `exit(0)`，表现是**门禁彻底失效**。

自查：改完 hook，跑一次**必须放行**的用例。只有拦截用例全绿，说明不了任何问题。

## 2. 命令失败被当成「没有变化」

`git diff HEAD` 在新仓库（无首个提交）会 fatal，若用 `cmd1; cmd2` 拼接，错误被吞掉，
函数返回空数组，调用方理解为「没有改动」→ 门禁静默通过。
本仓库的 `resolve-skills.mjs --diff` 踩过：早期版本用 `git diff HEAD`，新仓库无首个提交时 fatal，
错误被 `;` 吞掉，函数返回空数组。

自查：在**没有提交**的仓库里跑一次依赖 git 的检查，看它是报错还是返回空。
失败必须报错，不许退化成「通过」。

## 3. 拦截类用例全绿其实是崩溃

脚本崩在参数解析、崩在 import，退出码都是非 0，于是「应拦截」的断言全部满足。
本仓库 `guard_command` 的根路径 bug 就是这样被掩盖的：3 个拦截用例全绿，1 个放行用例立刻暴露。

自查：负向用例除了断言退出码，还要断言**命中具体错误信息**。

## 4. 注释里出现 `*/`

在 JSDoc 里写 `.ai/tasks/*/state.json`，其中的 `*/` 提前闭合注释块 → SyntaxError。
中文正则、glob 示例、`**/*.md` 都容易踩。

自查：`node --check` 全部脚本；`rg -n '^\s*\*.*\*/' hooks scripts`。

## 5. 例外没有到期日

allowlist 只写命令/路径 + 原因，不写日期，临时例外就变成永久后门，
且没人记得它为什么存在。

自查：例外文件必须是三段式 `<目标> | <原因> | <YYYY-MM-DD>`，且代码里比较日期，过期自动失效。

## 6. 规则太宽，第一次就被当噪声关掉

`\bany\b` 命中 license 头里的 "by any medium"；`-i '\bor\b'` 命中 XML 英文注释。
一条规则只要产生 30% 误报，团队就会整体关掉它，连真问题一起消失。

自查：新规则先在**真实代码库**跑一遍，抽样看前 10 条命中是否都是真问题。
命中即候选，不是判决——这句话要写进规则说明里。

## 7. 门禁与 CI 判定不一致

hook 校一套、CI 校另一套，CI 更松 → 「本地被拦、提交却能过」，门禁沦为提示。

自查：两边 import 同一个 `hooks/lib/verify.mjs`。任何校验逻辑出现在两处，就是分歧的开始。

## 8. 只做 warn 不做阻断

本该阻断的规则写成「提示一下」，三个月后没人看提示，行为回到没有门禁的状态。

自查：问一句「这条规则违反时的后果，是不是可以接受一次？」不能接受就必须阻断；
实在无法可靠判定，就降级成建议并**从硬规则表里删掉**，不要留着占位。

## 9. 拿非持久事实当证据（mtime 进 CI）

`git` 不保存 mtime。CI 全新 checkout 后，所有文件 mtime 都是检出时刻，按路径顺序略有先后。
于是「日志晚于源码」这条规则在 CI 上由检出顺序决定：`files: []` 的统一验证项直接
「找不到任何已改动的源码文件」，声明了 files 的则时红时绿。
**表现是合规 PR 被判红**——这比门禁失灵更快让人整体关掉它。

自查：问「这个判据在 `git clone` 出来的目录里还成立吗」。不成立的，只能留在本地 hook，
CI 侧换 git 可复现的事实（文件是否存在、是否入库、退出码）。本仓库的 `verify.mjs` 用
`mode: 'local' | 'ci'` 显式区分，不靠猜。

## 10. 依赖工具载荷里不存在的字段

PreToolUse 的载荷由 CLI 的工具 schema 决定。TodoWrite 的入参是
`{content, status, priority}` 且 schema **strict**：我们想要的 `id` / `audit` / `verify`
既传不进来，模型也不会凭空生成。上一版的 `validate_todo` 就是这样：正则永远不命中，
hook 恒放行，只在自造 payload 的测试里"有效"。

自查：把门禁挂到**你自己拥有的数据**上（本仓库是 `state.json`），不要挂在第三方工具的
输入结构上；写测试时必须用真实 schema 的样例，不能用自己编的字段。

## 11. 只给一个 CLI 接线，体检还报绿

hook 只写进 `.claude/settings.json`，`.zcode/` 下什么都没有，而 ZCode 不读 Claude 的 settings。
结果 ZCode 会话里三道门全不存在，`AGENTS.md` 却写着「hook 硬拦」，`doctor` 还显示
「✓ hook 已注册 4 个」——因为它只查了一个文件。

自查：接线本身也要单一源 + 生成 + 漂移检测（本仓库：`hooks/hooks.manifest.json` →
`build-hooks.mjs`）；`doctor` 按 CLI 逐个查，不是查到一个就算。
还要注意各家开关不同：ZCode 必须 `hooks.enabled: true`，工作区 hook 还需人工信任。

## 12. 配置键没有消费者

`modelTiers`、`requireVerifyLog`、`verifyFreshnessHours`、`trustLevel`、`defaultFlowTier`、
`srcGlob` 曾经全是空转：文档拿它们当承诺，代码里没有任何引用。
这比"没有这个功能"更糟——它让人以为已经配了。

自查：`doctor` 里有「配置键均有消费者」一项，键名必须出现在 `hooks/` 或 `scripts/` 的源码里。
新增配置键时同时给出消费者，否则不要写进配置。

## 13. 门禁堵死自己给的出路

`guard_command` 拦住 `.env` 并提示「改用 `.env.example`」，而 `guard_write` 的
`**/.env.*` 又把 `.env.example` 一起拦了。两道门互相打脸，用户按提示操作永远过不去。
同类问题：自救提示里写了不存在的路径（`.claude/hooks/allowlist.txt`，真实路径是
`hooks/allowlist.txt`）。

自查：每条 deny 提示里的"该怎么做"，必须有对应**正向测试**证明它真的能过。
提示文案里的路径要能被 `grep` 验证存在。

## 14. 用黑名单挡命令，只挡了教科书写法

`rm -rf /` 被拦，`rm -fr /`、`rm -r -f /` 放行；`git push --force` 被拦，
`git push origin +main:main` 放行；`curl … | sh` 被拦，`wget -qO- … | bash` 放行。
黑名单的失效方式是把"等价写法"漏在外面。

自查：每条规则写完后，先自己想三种等价变形（反序、分离、别名）各测一遍；
`test/hooks.test.sh` 里每个绕过形态一条用例。

## 15. 状态枚举不闭合，拼错的状态变成免检

校验器只挑 `completed` / `done` 处理，其余值一律跳过——本意是放过 pending/doing，
实际连 `complted`、`Complete` 一起放过了。拼错状态的 TODO 不触发证据校验、
不进完成统计，任务在账面上消失，CI 照样绿灯。同类故障：stage=done 不核对
退出条件，收尾声明与 TODO 明细互相矛盾也没人拦。

自查：任何"只对某些值校验"的分支，先写明合法值全集并**先判非法再分流**；
枚举外的值必须显式报错，不能静默 continue。声明型的退出条件（stage=done）
要有对应的机器核对，哪怕只核对"TODO 是否全部收尾"这个最低限度。

## 16. 把声明当门禁（writes 有名无实）

`agents/*.agent.md` 的 `writes` 字段看起来像写入边界，运行时却拦不住任何东西：
PreToolUse 载荷里没有 agent 名，`guard_write` 判不出是谁在写。
持有 fs.write 的文档类 agent（如 spec-reviewer，声明只写 `docs/02-features/**`）
用 Write 照样能覆盖未受保护的业务源码。同类故障：配置里声称"只读"的注释、
文档里的"只能写 docs/"——判据不存在，约束就不存在。

自查：问一句"这条约束的判据是什么、谁来执行"。答不出执行者的，明确标注为
交接契约（人评审 + CI diff `.ai/writes.json` 兜底），不要写成"硬限制"。
要真收紧只有两条路：裁 capabilities（生成期把工具裁掉），或进程级隔离
（沙箱 / 容器 / 独立工作树）——后者成本高且跨 CLI 难一致，落地前不要承诺。

## 17. 新流程只写在文档里，state 与 CI 都没有判据（流程衰减）

变更/修复这类分支流程最容易长成"README 里有完整表格，state.json 里没有字段，
ci-verify 里没有一条检查"。前两周大家还照着走，第三周弱模型接手、赶工上线的
change 不带基线、bugfix 没有回归测试，绿灯照常——流程退化成阅读理解题。
和 §16 是同根：**没有执行者的流程 = 建议**。判据存在才能叫流程，否则叫愿望。

自查：每新增一个任务类型 / 流程分支，同批问三件事——init/建档时校验什么？
state 里多哪个字段？完成态由谁（guard_state + ci-verify）判哪几条？
三问答不全就先别发布流程文档。反过来也别过度：机器只判"有没有"（字段非空、
TODO 存在），"对不对"（影响分析质量、档位选得合不合理）归 CR 人审，别造门禁剧场。

## 18. 归属靠"扫目录"猜，而不是靠"生成器声明"

装/卸类工具几乎都会犯：装完之后回扫产物目录，把扫到的一律记成"我装的"。这个口径分不清
"我生成的"和"用户原本就有的"——用户手写的 `.claude/commands/deploy.md` 被记成我们的，
`remove` 时连 hash 都护不住：hash 是对**用户文件**在安装时算的，天然"未改动"，于是一路放行。

判据必须由**产生方**给出：生成器用 `--manifest` 回报它写了哪些文件，卸载只认这份清单；
扫描最多作降级路径，且要在使用当场说明"此口径分不清归属"。

自查：任何"这些文件是我的"的判断，问一句来源是**声明**还是**推断**。
推断出来的不删，只提示；`foreign` 名单（安装前就存在）比任何事后推断都可靠。

## 19. 状态机停在 blocker 上，却没有"回来的路"

门禁 fail 就停住等人，这是设计。但**停下来之后呢**？真实项目（TDC 第一个任务）停在 adr、
8 条决策等人裁决；用户回来后唯一的办法是手改 `state.json` —— 而手改正是门禁最该防的动作：
漏 `resolved_by`、忘重跑 gate、顺手把 `stage` 推到下一阶段，谁也不知道这次推进有没有依据。

判断标准：**每一个"停下来"的分支，都要有一条命令能把人接回去**。这条命令必须

- 能把"缺什么"原样列出来（不是让人回去翻日志）；
- 回填时必须记名（无记名决策 = 幽灵决策，事后无法区分人拍的板与模型自己认的）；
- 回填后**重跑**能机器判的那条门禁，而不是相信调用方说"我改好了"；
- 推进阶段时留下 `stage_history`，让"谁在什么时候因为什么推进"可查。

没有这条路的状态机，最终都会被绕开——绕开的方式就是手改 JSON。

## 20. 规则共用一段建议文案

15 条高危命令规则共用一段"强推类改用 --force-with-lease；跳过测试类 flag 没有等价形式"。
拦到 `-DskipTests` 时，提示在讲强推——被拦的人照着提示修，修不好，最后只能去关规则。
文案错位不是安全漏洞，但它让门禁从"教人改对"退化成"挡路"。

判据：`hint` 必须挂在**规则自己**身上（`{pattern, hint}`），通用兜底只保留"唯一确定正确的出路"。
同理，观测数据必须能区分**来源**：自测探测与真实拦截混在一个账本里，"误拦率"就没有分母。

## 21. 停点不分档：把"能先干的"也当成闸门

真实数据：TDC 停在 adr，8 条决策同权平铺，输出末行是 `仍卡在 D1、D2、D3、D4、D5、D6、D7、D8、B1`。
可 D2 的建议自己写着「先做 T1 盘点再定；**盘点本身不依赖决策**」——它根本不该挡路，却被算成第 9 道闸门。
人看到一排红点，正确反应是"回头再说"，停点于是失效。

更根本的是**呈现与输入的错位**：屏幕上印 `磁盘/存储 · CPU · 内存 · …`，要输入的却是
`--decide "D1=磁盘/存储+CPU+内存"`；人得把 `·` 拆开再用 `+` 拼成另一个串。
显示格式与输入格式不同构，每一步都在制造出错机会。

判据：

- 停点必须按**是否挡路**分档（必须现在定 / 可以先干再定 / 按建议默认即可），
  档位来自显式字段 `blocking` `defer_until` `default_ok`，**不从建议文本里猜**——
  猜错等于替人授权；
- 呈现用的编号必须就是回填用的编号（`options` 归一成 `{id,label}`），
  决策值校验必须落在选项内（否则 `options` 只是装饰）；
- 停下来的信息要落在**文件**里（`DECISIONS.md`），不能只活在一次 stdout：
  关掉终端就没了、手机上处理不了、也没法转给同事。

## 22. 生成式文件刷新时冲掉人的编辑

决策单是"生成物"，但**人会把内容填进去**——它同时也是"人的输入"。
每次 `resume` 都重写它（为了保持幂等、去掉已决项），一刷新就把人填了一半的答案冲掉。
冲一次，人就不会再用它了。

判据：生成物若承载人的输入，刷新前必须**读出并比对已有内容**：

- 有未应用的编辑 → 不覆盖，点名提示"先用 xx 读回来"；
- 无编辑 → 内容有变才写（避免 mtime 噪声）。
  `manifest.generated` 的归属问题（§18）是同一个道理的另一面：**谁的内容，谁说了算**。

## 23. 阶段名不在链上：状态机外的任务

`init-harness.sh` 建任务时写 `stage: "intake"`，而阶段链是 `rs → wbs → … → done`——
"intake" 不在任何链上。后果不是报错，是**静默**：`resume` 查不到"下一阶段是谁"，
所有"按阶段"的判据一条都不命中。同一形态还有人手写的 `fs-review`（连字符，链上是 `fs_review`）：
CI 只判 todos，阶段名拼错照样绿。

判据：

- 阶段名、档位、风险级都是**枚举**，不是自由字符串：校验器必须有一份链，写错即 fail；
- 这份链只能有**一份**（`hooks/lib/verify.mjs`）。存量教训：本地脚本、CI、init 各存一份时，
  它们一定会漂移，而漂移的那份就是谁也拦不住的那条路；
- 建任务时的起始阶段必须是链首，不能自造一个"还没开始"的名字。

## 24. 推进动作替门禁下结论

`resume --advance` 曾把 `gate: pass:false` + 2 个未完成 TODO 的 impl 直接推进 review，
并在 `stage_history` 里记成 `impl/pass`。真实事故的形状是：**门禁的结论被推进动作改写**。

它比"没有门禁"更危险，因为它留下一条看起来合规的 history。

判据：

- 推进的前提是"这一阶段的门禁**已评估且全 pass**"，而不是"没有未解 blocker 了"；
- 评估结论必须来自 `gate_result.checks` 的实际内容，不能由"本次没报错"推出 pass；
- 换阶段后旧结论不顺延（`gate_result.stage` 与新 stage 必须对得上）；
- 推进失败时**一个字节都不写**——半写状态比不写更难排查。
- **退出条件 ≠ 写入条件**：`impl` 里还有 pending 是进行中的常态，把它做成写盘门禁，
  人就不敢记进度；反过来 `done` 里留未收尾的 TODO 必须拦。同一条判据挂错位置会反向出事。

注意别推到另一头：要求"必须有 gate_result"最省事的满足方式是手写 `{pass:true}`，
那就变成了 §16。所以 CI 侧只判"记了失败却当成功交付"，不判"你根本没评估"（后者归人审）。

## 25. 分档只改了显示，判定还按一档算

停点做了三档（必须现在定 / 可以先干再定 / 按建议默认），屏幕上分得好好的，
但 `canAdvance` 仍然按"未解 blocker 数 === 0"算——分档白做，第二节照样挡路。

同型还有**批量出口绕过枚举**：`--decide` 校验选项编号，`--accept-suggested`
却把建议原文写进 `decision` 并留 `decision_ids: []`。同一个字段两种口径，
严的那条路就形同虚设。

判据：

- 分档必须同时进**呈现**和**判定**：档位不是文案，是 `canAdvance` / exit code 的输入；
- 任何"批量/默认/推荐"通道都必须走与逐条输入**完全相同的解析函数**，
  解析不了就跳过并点名，不给假默认；
- 判定改动后，原有测试里"期望 exit 3"的断言必须重新看一遍——
  它们如果没变，说明判定其实没改。

## 26. 观测面只写不读

`deny.jsonl` 记了每一次拦截，但没有任何读取端。写了没人看，等于把最密集的改进信号
丢进一个打不开的抽屉："这条规则误拦多不多"永远只能靠印象争论。

同型更常见：`ledger`、`metrics`、`audit log` 都在写，只有写的那一半有代码。

判据：

- 有写入端就必须有读取端（`npm run ledger:report`），哪怕只是一行聚合；
- 统计要按 **source** 分开：自测流量混进真实基线，账本立刻失去意义；
- 记录粒度要能回答问题：只记"哪个 hook 拦的"得不出误拦率，得记**哪条规则拦了谁**；
- 出现"同一条规则拦了 N 次"就要回看原话——误拦不会自己消失，只会让人学会绕过门禁。

## 27. 解析外部输出时把"数据位"当成空白

`git()` 辅助函数对整段 stdout 做了 `.trim()`，于是 `git status --porcelain` 的
**第一条**丢了状态位前导空格（`" M pom.xml"` → `"M pom.xml"`），随后固定 `slice(3)`
就多切一个字符：`pom.xml` 变成 `om.xml`。

后果不是"少一条提示"，是判据整条失准：`INFRA_RE` 匹配 `pom.xml`，切坏后永远匹配不上——
**最该抓的那个基建文件，恰好是字母序第一条**。

判据：

- 解析结构化输出（porcelain、CSV、固定列宽的表格）时**只能裁尾，不能裁头**；
  实在要裁，按字段位置切，不要先 trim 再切；
- 断言要覆盖"第一条"：契约里"第一条"最容易和别的条目长得不一样（前导空格、BOM、表头）；
- 同一函数被多处复用时，看每一处对"前导空白是否属于数据"的假设是否一致。

## 28. 包装器吃掉了自己的入参

`verify-run.sh` 统计 surefire 计数时写了 `set -- $parsed`，覆盖了脚本自身的位置参数，
随后 `echo "# cmd: $*"` 打出来的是 `7 0 0 0`——**命令字段变成了测试计数**。

越是有 surefire 报告的 Maven 运行越必然踩中，而"有报告"正是它被设计来解决的场景。

同型的还有：`shift` 之后再用 `$@`、循环里复用 `$1`、函数内改 `$*` 后调用方还指望原值。

判据：

- 需要保留的入参先落成具名变量或数组（`CMD=("$@")`），再动位置参数；
- 拆字段用 `read -r a b c <<<"$x"`，不要用 `set --`；
- **包装器/适配层一定要有用例**：它是所有下游判据的输入源，坏了没有第二道防线。
  "它只是十几行 shell"不是免测理由，恰恰因为它短、又被所有人绕过。

## 29. 契约只查一个方向

契约文档原来只做单向体检：**文档标成"判据"的字段必须在代码里有读者**。
于是长出了反向的坑——`checkStageExit()` 已经拿 `deviations` / `known_issues` 拦人了，
而文档还写着"deviations 不是门禁输入"、`known_issues` 连登记都没有。

两个没人知道要写的字段 = 两处默认空转的门禁，而体检全绿。

判据：

- 契约必须双向校验：文档→代码（标了判据就得有人读）、代码→文档（读了就得登记并定档）；
- 反向扫描前先剥字符串和注释，否则注释里的 `state.json` 会被读成字段 `json`；
  扫全仓会带进 `fs.stat` 的 `st.isDirectory` 这类同形异物——**范围要小到没有假阳性**，
  一条开始报假阳性的检查，最后一定被人加白名单加到消失；
- 扫描范围要写进注释：为什么只扫 `verify.mjs`，代价是什么。

## 30. 规则写了，但没有用例

`#18 未声明基建文件` 这条规则写了很久，**没有任何用例**。它唯一可能失败的路径
（字母序第一条被切坏）因此一直没人发现——规则、测试、真跑三者缺一，
效果等于"以为有门禁"。

判据：

- 每条判据至少两条用例：该拦的拦、该放的放。只测"拦得住"不够（脚本崩溃也返回非 0）；
- 新规则要能被一个**具体的历史故障**复现：说不出来源故障的规则，通常也没人验证过它；
- 改解析层（§27、§28）时必须回头看依赖它的规则是否还有效——它们可能一起静默失效。

## 31. 豁免通道比门禁更容易满足

"改动必须声明进某个 TODO 的 files"这条规则，最便宜的满足方式是**建一个登记任务**，
把 60 个文件列进去，然后它自己的收口判据是空的（没 verify 日志、stage_history 空）。

规则一旦可以被"新建一个东西"满足，它就会教人绕过，而不是教人收敛。

判据：

- 豁免要有**可核对的来源**（安装清单、工具自身文件），而不是"某人写了一句声明"；
- 结构性豁免（目录、通配、清单）要单独审：一条声明豁免一大片时，先问它覆盖了什么；
- 登记型任务必须有收口条件（谁在什么时候、按什么依据认定这批文件归属于此），
  否则它就是一条免检通道。

## 32. 工具产出自己会判红的状态

`resume --advance` 推进后保留了上一阶段的 `gate_result`。此后 `ci-verify` 的
"gate_result 必须与当前阶段一致"一开，**工具刚写下的 state 立刻被判红**，
只能靠人手工清。TDC 那份 `stage=impl` + `gate_result.stage=adr` 就是这么来的。

判据：

- 工具写下的状态必须能通过自己的门禁：改完推进/init/迁移逻辑，用它的产物跑一遍 CI；
- "保留旧记录"听起来比"清空"保守，但如果旧记录的语义是"本阶段已评估"，保留就是伪造；
- 清空要清成**显式的未评估**（`checks: []` + 阶段名对齐），不是留个空格让人猜。

## 33. 例外清单由门禁自己写

`hooks/write-allowlist.txt` 是给"确实需要例外"留的出口，但里面有一条是门禁自己
（或为门禁自己）发出去的通行证。自授权闭环的意思是：**规则约束谁，谁就能改规则**。

判据：

- 例外清单的写入者必须与被执行者分离：人或独立评审，不能是执行门禁的那段代码/那个会话；
- 每条例外要有到期日与理由，过期自动失效（本仓库已有此机制，问题在**发行方**）；
- 审例外清单时看"谁写的"，不只看"写了什么"。

## 34. 用例只证有、不证无

"表血缘能提取到 td_user" 是正例，"血缘里不许出现 @Param 的参数名" 才是判据。
只写正例的用例等于给实现发了一张"随便多加东西"的许可证——分析器在 TDC 上
112 个"表"里混进 25 个列名，就是这么过去的：夹具只断言"包含 td_demo/td_app"。

同一形态的另一种：**两条用例断言同一个条件**（Go 的两条都只判 `imports_unresolved===0`），
在报告里数起来是 2 条，实际覆盖 1 条。用例数不是覆盖度。

判据：

- 每条"提取/识别/收集"类规则至少一对断言：**应包含的**（精确集合，不是 `includes`）与**不应包含的**；
- 负例要埋真实干扰源：同一文件里的注释、参数名、日志字符串、被注释掉的语句——
  不是随便造个不相关的词；
- 计数类断言写恒等式（`resolved + unresolved + external + stdlib === parsed`），
  任何一类漏算都会破坏它，比逐个字段断言更难造假。

## 35. 阶段次序错了，门禁再严也补不回来

`STAGE_CHAIN` 曾把 `wbs` 排在 `fs_review` 之前。每一步都在自己的阶段里"通过"了，
结果整体是错的：WBS 要求每个叶子有可验收标准，而验收标准只能来自 FS 的行为定义——
**在未评审的输入上做完的阶段，每一步都合格，合起来不可用**。

判据：

- 问一句「这一阶段的输入是哪一阶段的输出」，答不上来的位置就是错的；
- 门禁只判"这一阶段做完了没有"，判不了"在错误的输入上做完"——次序本身要当判据，
  不要指望下游门禁发现上游选错了输入；
- 产物之间的引用要写成机器可读的（`spec_ref: fs#§4.2@blob`），才不会出现
  "WBS 指向一个 FS 里已不存在的小节"这种只有人肉才看得见的失联。

## 36. 判据的洞不表现为失败，表现为绿灯

完备性检查的路径判据曾是「不含空格且不含中文」才算路径，命中就 `continue`。
于是登记 `docs/需求 规格.md`（文件不存在）时，检查退出码 0——
**它一个字节都没读，却给出了"完备性通过"**。所有检查都在正常运行，只是恰好在那个文档上没命中。

同类形态：链序改了，存量 history 按旧链记的，于是合规历史被判跳阶——
判据变更的净效果是逼人改历史或关掉检查。

判据：

- 改判据必须配一次**红灯复现**：新用例先拿旧实现跑，确认它真的红。没有这一步，
  分不清"判据有效"和"判据根本没命中"；
- "跳过的对象"要显式分类：放过是因为它不是目标，还是因为判据看不见它？
  后者一律改判红——读不出、解析不出、认不出，都是"没检查"，不是"检查通过"；
- 判据变更要问「谁的存量会被这次变更判红」，并为"过去是合法的"留一个具名位置
  （退休链、迁移豁免），否则人会在改历史和关检查之间二选一；
- 判据写完后先在自己最近的改动上跑一遍：自己都满足不了的判据，第一次上线就会被关掉。

## 37. 停机规则放在被停对象的里面（外部样本：Apse 2026-11-04 预算死锁）

Apse（TDengine 内部 Agent 编排框架）的事故：24 小时墙钟检查写在 `run_agent` 里，
`run_agent` 被 e4b-notify 调用、e4b-notify 在 tick 里——任何一层没接住 `BudgetExhausted`，
**停机就升级成整机停机**：tick 每轮崩在半路、索引回退到旧状态、同批任务永久卡住、
下一轮又重复检测重复失败。预算本身设得并不小，坏的是**停机判断的位置**。

一般形式（比事故本身更值得抄）：

- 停机规则要放在**被停对象的上一层**：预算/重试/超时由调度层判定，不由被停的执行体自己报告；
- 停机动作本身不能抛异常——它是"保护"，不是"业务"，保护路径挂了等于没有保护；
- 失败信息**先落盘再传播**：异常先变成一条事件/日志，再决定要不要打断控制流；
- 墙钟与成本分开计：人的等待、外部系统的等待不累计墙钟（否则一次人休一天 = 任务全灭），
  usd/tokens 持续累计；
- 阻塞要有"回来的路"：budget-blocked 类终态加 TTL 自动回流程，永久 Blocked 在生产上
  等于"没人处理的收件箱"，越积越没人看。

自查：找到你的每个停机点（预算、超时、重试上限、熔断），沿调用链向上数一层——
停机判断在那里吗？停机路径上有一个可能抛异常的调用吗？

## 38. 证据链的退出码会被管道洗绿

`.ai/verify/RV2.log` 记录的是一条**真实跑过的**命令：

```
bash -c 'bash test/a.sh | tail -1 && bash test/b.sh | tail -1 && ... && echo GATE_EXIT_OK'
```

`false | tail -1` 的退出码是 `tail` 的 0。四个套件全红，链条照样走到 `echo GATE_EXIT_OK`，
日志头照样写 `exit_code: 0`——**判据不报错，才是这类事故最贵的地方**。同一批里还有一份
`T9.log`：整条命令 `>/dev/null` 只 `echo OK`，日志里除了 `OK` 没有任何断言计数。
"我跑过了"和"它跑通了"是两件事，日志必须能分开它们。

判据：

- 包装器（`scripts/verify-run.sh`）自己 `set -o pipefail` 只管自己——命令是子进程。
  要 `export SHELLOPTS` 才会传导给子 bash；`sh -c` 不认，所以判据只认日志头的退出码；
- 写"多套件串联"的命令时，别用 `| tail -1` / `| head` 收尾。要看尾部就整段重定向到文件再 `tail`；
- 证据日志里必须留下可对账的断言计数（`结果：N 通过`、`# tests: total=`），
  只有 `echo OK` 的日志不算证据，算自我声明；
- 给包装器写一条会红的用例（`bash -c 'false | tail -1'` 必须非 0），否则这条修复
  在下次重构时会被无声地改回去。

自查：把命令里每个 `|` 都问一遍——如果前一段失败了，链条会停吗？退出码是谁的？

## 39. 解析成功不等于形状正确

`projectDirs()` 曾经只判「是不是合法 JSON」。于是这两种手滑都 exit 0：

- `{"projects":"backend"}`（类型写错）→ 不是数组 → 落到 `Object.values(c.stacks || {})` = `[]`
- `{"projects":[{"id":"a"}]}`（漏 `dir`）→ 被 `filter` 静默丢掉

结果和"JSON 坏掉"一模一样：路由退到 `fallback_paths`，审核覆盖面悄悄变窄，门禁还是绿的。
**能解析的坏配置比不能解析的坏配置更危险**——后者会报错，前者只会安静地少审几个文件。

判据：

- 判"存在且格式正确"时，把形状逐层声明出来：容器是数组还是对象、每项必填哪个键、
  空字符串算不算有值。没有形状声明的 `JSON.parse` 等于没有校验；
- 静默过滤（`map/filter` 掉不合法项）必须配一个计数或抛错：被丢掉几项、为什么丢；
- 每个形状洞配一条负向用例，并做变异验证（退回旧实现必须变红）；
- 同一个函数被多个入口调用时，异常的处置口径要写死并各自有用例——
  exit 2 与 HTTP 500 是两种不同的"失败"，后者会让上游反复重投。

自查：配置里每个可选字段，写错类型时程序是报错还是"看起来没事"？

## 新增规则前必须回答的四个问题

1. **判定输入是什么？** 文件存在 / 退出码 / mtime / 正则命中 —— 有一项做不到，就不是硬规则。
2. **误报时人怎么绕过？** 没有合法绕过的规则，会在第一次误伤后被整体删除。
3. **它和现有规则重复吗？** 同一条约束挂多处硬门禁，会互相抵消（一处放行即全部放行）。
4. **谁来维护阈值？** 写死在校验器里的阈值，半年后没人敢动。

## 不要在 hook 里做的事

- **语义判断**：`feature_complete`、`quality_clean` 这类无法机器判定，硬写只会催生形式化断言。
- **调外部服务**：网络抖动会让门禁时好时坏，dev 机断网直接卡死。
- **读大文件全文**：只看日志头 `LOG_HEAD_BYTES`，几十 MB 日志会把 PreToolUse 拖成秒级。
- **自动修改文件**：hook 只做判定与拒绝，不替人改代码——否则问题被隐藏而非解决。
