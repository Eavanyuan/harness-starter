# 门禁失效点自查

这 8 条全部来自本仓库与同类项目的真实故障，不是设想。
写新 hook、改判定条件、加规则之前逐条对一遍。

## 1. 根路径多退/少退一层

hook 在 `hooks/` 下，`resolve(dirname, '..')` 是仓库根；写成 `'../..'` 就读不到 `harness.config.json`。
读不到配置时如果走了 `deny`，表现是**所有命令都被拦**；如果走了 `exit(0)`，表现是**门禁彻底失效**。

自查：改完 hook，跑一次**必须放行**的用例。只有拦截用例全绿，说明不了任何问题。

## 2. 命令失败被当成「没有变化」

`git diff HEAD` 在新仓库（无首个提交）会 fatal，若用 `cmd1; cmd2` 拼接，错误被吞掉，
函数返回空数组，调用方理解为「没有改动」→ 门禁静默通过。
本仓库的 `check-rules.py --diff` 与 `resolve-skills.mjs --diff` 都踩过。

自查：在**没有提交**的仓库里跑一次依赖 git 的检查，看它是报错还是返回空。
失败必须报错，不许退化成「通过」。

## 3. 拦截类用例全绿其实是崩溃

脚本崩在参数解析、崩在 import，退出码都是非 0，于是「应拦截」的断言全部满足。
本仓库 `guard_command` 的根路径 bug 就是这样被掩盖的：3 个拦截用例全绿，1 个放行用例立刻暴露。

自查：负向用例除了断言退出码，还要断言**命中具体错误信息**。

## 4. 注释里出现 `*/`

在 JSDoc 里写 `.ai/tasks/*/state.json`，其中的 `*/` 提前闭合注释块 → SyntaxError。
中文正则、glob 示例、`**/*.md` 都容易踩。

自查：`node --check` 全部脚本；`rg -n '^\s*\*.*\*/' hooks scripts`。

## 5. 例外没有到期日

allowlist 只写命令/路径 + 原因，不写日期，临时例外就变成永久后门，
且没人记得它为什么存在。

自查：例外文件必须是三段式 `<目标> | <原因> | <YYYY-MM-DD>`，且代码里比较日期，过期自动失效。

## 6. 规则太宽，第一次就被当噪声关掉

`\bany\b` 命中 license 头里的 "by any medium"；`-i '\bor\b'` 命中 XML 英文注释。
一条规则只要产生 30% 误报，团队就会整体关掉它，连真问题一起消失。

自查：新规则先在**真实代码库**跑一遍，抽样看前 10 条命中是否都是真问题。
命中即候选，不是判决——这句话要写进规则说明里。

## 7. 门禁与 CI 判定不一致

hook 校一套、CI 校另一套，CI 更松 → 「本地被拦、提交却能过」，门禁沦为提示。

自查：两边 import 同一个 `hooks/lib/verify.mjs`。任何校验逻辑出现在两处，就是分歧的开始。

## 8. 只做 warn 不做阻断

本该阻断的规则写成「提示一下」，三个月后没人看提示，行为回到没有门禁的状态。

自查：问一句「这条规则违反时的后果，是不是可以接受一次？」不能接受就必须阻断；
实在无法可靠判定，就降级成建议并**从硬规则表里删掉**，不要留着占位。

---

## 新增规则前必须回答的四个问题

1. **判定输入是什么？** 文件存在 / 退出码 / mtime / 正则命中 —— 有一项做不到，就不是硬规则。
2. **误报时人怎么绕过？** 没有合法绕过的规则，会在第一次误伤后被整体删除。
3. **它和现有规则重复吗？** 同一条约束挂多处硬门禁，会互相抵消（一处放行即全部放行）。
4. **谁来维护阈值？** 写死在校验器里的阈值，半年后没人敢动。

## 不要在 hook 里做的事

- **语义判断**：`feature_complete`、`quality_clean` 这类无法机器判定，硬写只会催生形式化断言。
- **调外部服务**：网络抖动会让门禁时好时坏，dev 机断网直接卡死。
- **读大文件全文**：只看日志头 `LOG_HEAD_BYTES`，几十 MB 日志会把 PreToolUse 拖成秒级。
- **自动修改文件**：hook 只做判定与拒绝，不替人改代码——否则问题被隐藏而非解决。
